# ADR-002: Модульный монолит по умолчанию, микросервисы только по необходимости
_Дата: 2026-08-17_
_Статус: принято_

## Контекст
Выбор базовой архитектуры для новых проектов. Существует тренд на микросервисы, однако на старте они часто вносят ненужную сложность.

## Решение
Начинать все новые проекты с архитектуры **Модульный монолит** (Modular Monolith) с жесткими границами между доменами. 
Переход на микросервисы (как это было сделано в проекте Valeur) должен осуществляться только при наличии явных бизнес-требований:
- Необходимость масштабирования конкретного домена независимо от остальных.
- Изоляция данных на уровне разных баз (Enterprise Multi-tenancy).
- Разные стеки технологий (например, AI-сервис на Python и CRUD на Java).

## Причины
- **Снижение когнитивной нагрузки:** Не нужно думать про распределенные транзакции (Saga, 2PC), идемпотентность, и проблемы сети (latency, circuit breakers).
- **Простота деплоя:** Один артефакт, один пайплайн.
- **Рефакторинг:** Гораздо проще переносить классы между модулями внутри одного процесса, чем менять контракты API между микросервисами.

## Последствия
- Потребуется строгая дисциплина (и инструменты вроде ArchUnit), чтобы модули внутри монолита не превратились в спагетти.
- При достижении лимитов монолита потребуется осознанный и сложный процесс "распила".
