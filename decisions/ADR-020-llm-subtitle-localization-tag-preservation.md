# ADR-020: Конвейер локализации субтитров через LLM и алгоритм TagPreservator

## 1. Контекст и проблематика
При автоматическом переводе субтитров кинофильмов на национальные языки (казахский язык в проекте testCinema / INSIGHT) с использованием больших языковых моделей (LLM) возникают три фундаментальные проблемы:
1. **Искажение и потеря разметки форматирования:**
   LLM при переводе текста часто искажают или удаляют встроенные HTML-теги оформления (`<i>`, `<b>`, `<font color="...">`) и служебные знаки музыкального сопровождения (`♪`). Это ломает отображение субтитров в плеере.
2. **Нарушение выравнивания строк (Line Alignment Mismatch):**
   Субтитры жестко привязаны к временным меткам (таймкодам). Если модель объединит две реплики в одну или разобьет строку на две, весь последующий тайминг фильма смещается, делая субтитры несинхронными.
3. **Лимиты внешних API и стоимость токенов:**
   Сервис OpenSubtitles на бесплатном тарифе дает жесткий лимит 20 скачиваний в сутки, а перевод полнометражного фильма (1 500 – 2 500 строк) через синхронный GPT-4 API создает высокую финансовую нагрузку.

## 2. Архитектурное решение: Микросервис SUBTITLE-TRANSLATOR
Реализован отдельный сервис на Python FastAPI (`subtitle-translator`) со следующими архитектурными решениями:

### 2.1. Каскадный поиск (Waterfall Ingestion) и Quota Backoff
- Java-воркер (`SubtitleMetadataService`) выполняет поиск дорожек по каскаду: `kk` $\to$ `ru` (для стран СНГ) $\to$ `en`.
- При получении `OpenSubtitlesQuotaExceededException` воркер активирует защитный замок (`resumeAt = now + 24h`) и переходит в режим сна без падения приложения и без повторных штрафных запросов к API.

### 2.2. Препроцессинг: алгоритм токенизации TagPreservator
Перед отправкой чанка диалогов в LLM:
1. Регулярные выражения вырезают все открывающие/закрывающие теги и специальные символы, заменяя их на стандартизированные XML-токены: `<0>`, `<1>`, `<2>`.
2. Модели передается строгий системный промпт: сохранять количество строк и неизменность токенов `<N>`.
3. После получения ответа алгоритм детокенизации возвращает оригинальные теги на их точные позиции, а галлюцинированные теги вычищаются.

### 2.3. Постпроцессинг: аудит качества TranslationValidator
Результат валидируется перед фиксацией:
1. **Строгая проверка числа строк:** Если число переведенных строк не равно исходному $\implies$ генерация `AlignmentError` и повторная попытка с меньшим размером чанка.
2. **Проверка на пустые строки:** Ни одна реплика не должна быть утеряна.
3. **Детекция утечки непереведенного текста (Latin Leakage):** Поиск латинских слов длиннее 4 символов. Если слово не входит в глобальный белый список (`WEBVTT`, `OK`) и отсутствует в сгенерированном глоссарии имен собственных, чанк помечается на доработку.

### 2.4. Провайдеры: OpenAI Batch API и Google Gemini
- **OpenAI Batch API:** Используется для фонового перевода новых поступлений (скидка 50% на стоимость токенов с окном обработки до 24 часов).
- **Google Gemini 1.5 Flash:** Используется для быстрого перевода по требованию администратора.

### 2.5. Обратный вызов через Webhook
После успешной сборки VTT-файла сервис отправляет POST-запрос на Java Backend:
`POST /api/internal/subtitles/translation-complete` с заголовком `X-Internal-Secret`, обновляя статус в БД (`translation_status = 'success'`, путь к файлу, количество переведенных строк).

## 3. Последствия и преимущества
- **Позитивные:**
  - 100% сохранность таймингов и оформления субтитров в плеере.
  - Сокращение расходов на API в 2 раза благодаря Batch API.
  - Устойчивость к лимитам бесплатных тарифов OpenSubtitles.
- **Компромиссы:**
  - Асинхронная природа: перевод фильма занимает от нескольких минут (Gemini) до нескольких часов (OpenAI Batch).
