# ADR-017: Бюджетирование Памяти JVM и Тюнинг Metaspace в Контейнерах Fly.io

## Статус
Принято (Accepted)

## Контекст
Бэкенд JF-1C (Spring Boot 3, Java 17) развернут на платформе Fly.io на виртуальной машине с ограниченным объемом оперативной памяти (512MB RAM).
В ходе комплексного нагрузочного тестирования (Warmup + Full CRUD E2E) все функциональные модули системы (CRM, Billing, Invoices, Documents, Calendar, LMS, Analytics) были активированы одновременно.
Это вызвало резкий рост потребления памяти Metaspace до **126.5 MB**, что привело к срабатыванию алерта Grafana `metaspace-near-limit` (порог был настроен из расчета устаревшего лимита 128m).

Фактический лимит памяти Metaspace на запущенном контейнере составлял 160 MB (`jvm.memory.max = 167772160 bytes`), что давало запас всего 33 MB (заполнение 79%). Неконтролируемый рост Metaspace чреват фатальной ошибкой `java.lang.OutOfMemoryError: Metaspace` и падением процесса бэкенда.

## Анализ Проблемы
1. **Анатомия Metaspace**: В отличие от Java Heap (где живут бизнес-объекты и DTO), Metaspace хранит метаданные классов, структуры методов, таблицы констант, байткод и динамические прокси.
2. **Специфика Spring Boot + Hibernate**:
   - Spring Security генерирует CGLIB/ByteBuddy-прокси для `@PreAuthorize` и `@Secured` на каждом бине сервиса.
   - Spring Data JPA генерирует динамические реализации репозиториев на лету.
   - Hibernate компилирует HQL/JPQL-запросы и создает runtime-мапперы сущностей.
   - Thymeleaf и Jackson создают динамические резолверы и кэши структур сериализации.
3. **Поведение "Плато"**: Metaspace растет скачкообразно во время прогрева (warmup) при первом вызове каждого контроллера, после чего стабилизируется. Однако при динамической компиляции и шаблонизации требуется безопасный буфер.
4. **Ограничение контейнера (cgroup 512MB)**:
   - Общая память процесса = Heap (-Xmx) + Metaspace (-XX:MaxMetaspaceSize) + Native Memory (стеки потоков `ThreadStackSize`, буферы Netty/NIO, GC-структуры).
   - Если сумма превышает 512MB, Linux OOM-killer аварийно завершает процесс `kill -9`.

## Решение
1. **Явное задание лимита Metaspace в конфигурации Fly.io**:
   В `fly.toml` зафиксирован флаг:
   ```toml
   [env]
     JAVA_TOOL_OPTIONS = "-XX:MaxMetaspaceSize=256m"
   ```
2. **Бюджет распределения памяти контейнера (512 MB)**:
   - **Heap Memory (`-Xmx256m`, `-Xms128m`)**: максимум 256 MB для объектов приложения, сессий и очередей задач.
   - **Metaspace (`-XX:MaxMetaspaceSize=256m`)**: потолок 256 MB (типичное плато прогретого Spring Boot 3 составляет 130-150 MB, что оставляет комфортный буфер безопасности >100 MB).
   - **Native & Stack Memory**: ~64-96 MB (стеки легковесных потоков, DirectByteBuffer для I/O).
   - При превышении суммарного лимита ноды Fly.io масштабируется до 1024MB RAM (Scale VM), не допуская деградации.
3. **Калибровка Алертинга в Grafana**:
   - Порог алерта `metaspace-near-limit` перенастроен с абсолютного значения 120 MB на относительный порог: **> 85% от лимита** (при лимите 256m алерт срабатывает только при потреблении > 218 MB).
   - Добавлен параметр задержки `for: 5m` для фильтрации кратковременных всплесков инициализации.

## Последствия
### Положительные:
- Полностью исключен риск аварийного падения `OutOfMemoryError: Metaspace` при подключении новых модулей или массовой генерации PDF/Thymeleaf-документов.
- Устранены ложные срабатывания системы мониторинга при штатном прогреве классов.
- Сохранена жесткая изоляция памяти в рамках минимального тарифа Fly.io.

### Риски и Митигация:
- *Риск*: При росте Heap до 256 MB и Metaspace до 180 MB суммарный объем может приблизиться к границе cgroup 512 MB.
- *Митигация*: Мониторинг суммарного RSS через `container_memory_working_set_bytes`. При достижении 450 MB RSS принимается решение о вертикальном масштабировании машины до `shared-cpu-1x:1024mb`.
