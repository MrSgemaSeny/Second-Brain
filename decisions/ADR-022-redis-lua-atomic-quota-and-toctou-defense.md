# ADR-022: Атомарный Rate Limiting в Redis через Lua-скрипты (TOCTOU Defense) и инвалидация тарифного кэша

## Статус
Принято (Accepted)

## Дата
2026-09-16

## Контекст и проблематика
При аудите конкурентного доступа (Audit v2.0, P0) в `AiRateLimiter.java` была выявлена классическая уязвимость Time-of-Check to Time-of-Use (TOCTOU):
1. Проверка лимита и инкремент счетчика выполнялись как раздельные сетевые команды в Redis (`GET -> if (count >= limit) return false -> INCR`).
2. При параллельных запросах (например, 10 одновременных вызовов со вкладок браузера) несколько потоков одновременно считывали `count = 9`, проходили проверку и инкрементировали счетчик до `19` при лимите `10`.
3. Кэш тарифного плана пользователя `user_plan:<userId>` имел жесткий TTL 15 минут без механизма немедленной инвалидации. При переходе с PRO на FREE или истечении подписки пользователь мог продолжать бесплатно расходовать квоты тарифа PRO в течение 15 минут.

## Принятые решения

### 1. Атомарный Redis Lua-скрипт (Single Transaction Check-and-Increment)
Вся логика проверки лимита, инкремента и установки TTL перенесена в единый Redis Lua-скрипт, исполняемый атомарно на стороне Redis engine:

```lua
local current = redis.call('get', KEYS[1])
local limit = tonumber(ARGV[1])
local ttl = tonumber(ARGV[2])

if current and tonumber(current) >= limit then
    return -1
end

local newVal = redis.call('incr', KEYS[1])
if newVal == 1 then
    redis.call('expire', KEYS[1], ttl)
end
return newVal
```

- Если лимит исчерпан (`current >= limit`), скрипт немедленно возвращает `-1` без увеличения счетчика.
- Если квота доступна, атомарно выполняется `INCR`, для нового ключа выставляется TTL до конца суток (`secondsUntilMidnight()`), и возвращается новое значение.
- Исключена утечка квот и необходимость компенсирующих `DECR` откатов.

### 2. Динамический TTL и принудительная инвалидация кэша планов
- При любом изменении плана пользователя (Webhook успешной оплаты Stripe, отмена подписки, ручная смена роли) вызывается `redisTemplate.delete("user_plan:" + userId)`.
- TTL кэша плана рассчитывается динамически: `min(15 минут, время_до_окончания_подписки)`. Если до истечения подписки осталось 2 минуты, кэш живет ровно 2 минуты, исключая окно рассинхронизации прав.

## Последствия
- Положительные:
  - 100% гарантия соблюдения лимитов под любой параллельной нагрузкой (проверено стресс-тестами `AiRateLimiterAdversarialTest`).
  - Мгновенное применение изменений тарифа пользователя без 15-минутного окна задержки.
  - Снижение сетевого overhead между бэкендом и Redis (1 вызов Lua вместо 3 сетевых round-trips).
- Ограничения:
  - Redis должен поддерживать выполнение Lua-скриптов (поддерживается всеми версиями Redis 2.6+ и Valkey).
