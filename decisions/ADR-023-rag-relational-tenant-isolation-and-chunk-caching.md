# ADR-023: Реляционная изоляция арендаторов в pgvector (Tenant Isolation) и контентное кэширование чанков RAG

## Статус
Принято (Accepted)

## Дата
2026-09-16

## Контекст и проблематика
При аудите RAG и векторного поиска (Audit v2.0, P0/P1) были выявлены архитектурные риски:
1. **Хрупкая изоляция арендаторов (Tenant Isolation)**: фильтрация векторов осуществлялась через разбор JSON-метаданных `WHERE metadata->>'userId' = ?`. Ошибка сериализации JSON или некорректный синтаксис поля могли привести к межпользовательской утечке семантических векторов (IDOR в RAG).
2. **Отсутствие внешних ключей и индексов**: таблица `vector_store` не имела внешнего ключа на `users(id)`, что приводило к накоплению "осиротевших" (orphaned) векторов при удалении пользователей.
3. **Неэффективная полная переиндексация**: при любом изменении одного навыка или описания проекта метод `upsert()` удалял все векторы пользователя и вызывал внешний дорогостоящий API Jina AI для повторного вычисления всех эмбеддингов.

## Принятые решения

### 1. Реляционная колонка `user_id` и каскадное удаление (Flyway V29)
В миграции `V29__security_and_architecture_hardening.sql`:
- Добавлен выделенный реляционный столбец `user_id BIGINT NOT NULL`.
- Наложен внешний ключ `CONSTRAINT fk_vector_store_user_id FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE`.
- Создан B-Tree индекс `CREATE INDEX idx_vector_store_user_id ON vector_store (user_id)`.
- Все SQL-запросы поиска по косинусному расстоянию (`<=>`) переведены на строгое условие `WHERE user_id = ? ORDER BY embedding <=> ?::vector LIMIT ?`.

### 2. Контентное SHA-256 хеширование чанков (Chunk Content Caching)
- Для каждого фрагмента профиля (опыт, проект, навык) вычисляется криптографический SHA-256 хеш содержимого (`chunkHash = CryptoUtils.sha256Hex(content)`).
- Хеш сохраняется в JSON-метаданных вектора вместе с версией (`version = "1.0"`), моделью (`model = "jina-embeddings-v2-base-en"`) и размерностью (`dimension = 768`).
- Перед отправкой на векторизацию сервис сравнивает хеши новых чанков с уже существующими в БД:
  - Неизмененные чанки повторно не отправляются в Jina AI, экономя токены и время отклика.
  - Векторизуются только новые и модифицированные фрагменты.

## Последствия
- Положительные:
  - 100% защита от межпользовательской утечки векторов на уровне реляционной схемы PostgreSQL.
  - Автоматическая очистка векторов при удалении аккаунта (ON DELETE CASCADE).
  - Снижение нагрузки на внешнее API эмбеддингов до 80% при регулярных точечных правках резюме.
- Ограничения:
  - Требуется поддержка расширения pgvector в PostgreSQL 17.
