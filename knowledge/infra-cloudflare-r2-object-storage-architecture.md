# Инфраструктура: Объектное хранилище Cloudflare R2 для SaaS (Архитектурный паттерн)

## 1. Концепция и экономика хранилища (Why R2 over S3)
В архитектуре SaaS-платформ для бухгалтерского и финансового учета (JF-1C) хранение документов (акты, договоры, первичка, сканы чеков, выписки) в базе данных PostgreSQL в колонке `BYTEA` неизбежно приводит к раздуванию СУБД (bloat), замедлению создания бэкапов и нерациональному расходу оперативной памяти JVM.

### Сравнение с классическим AWS S3:
1. **$0 Egress Fee (Нулевая стоимость исходящего трафика):**
   - В AWS S3 каждый гигабайт скачанных клиентами документов тарифицируется по ~$0.09/GB.
   - В Cloudflare R2 исходящий трафик в интернет полностью бесплатный.
2. **Стоимость хранения:** $0.015 / GB в месяц (против $0.023 / GB в AWS).
3. **Совместимость с S3 API:**
   - 100% поддержка протокола AWS S3 (REST API, AWS SDK v2, Pre-signed URLs, Multipart upload).
   - Нет вендор-лока: миграция между R2, MinIO и AWS S3 требует только изменения `endpoint` и `credentials`.

## 2. Параметры подключения JF-1C (Production Setup)
- **Account ID:** Задается через переменную `${R2_ACCOUNT_ID}` в `.env` / Fly Secrets
- **S3 API Endpoint:** Задается через переменную `${R2_ENDPOINT}` в `.env` / Fly Secrets
- **Bucket Name:** `jf1c-documents` (`${R2_BUCKET_NAME}`)
- **Default Storage Class:** Standard
- **Public Access:** Disabled (доступ только по подписанным приватным ключам)
- **Access Model:** 
  - Приватный бакет без прямого публичного листинга.
  - Доступ на чтение/запись строго через IAM-токены и S3 Client Credentials (`${R2_ACCESS_KEY_ID}`, `${R2_SECRET_ACCESS_KEY}`).

## 3. Архитектурный паттерн: Гибридный доступ (Dual-Read / Shadow Write)

```
[ Клиент загружает файл ]
          │
          ▼
   [ Spring Boot ] ──(Потоковая передача без byte[] в RAM)──► [ Cloudflare R2 ]
          │                                                          │
          │                                                   (Генерация s3_key)
          ▼                                                          │
   [ PostgreSQL ] ◄──────────────────────────────────────────────────┘
   (Метаданные: fileName, s3_key, storage_provider='S3', content=NULL)
```

### Принципы обеспечения нулевого даунтайма:
1. **Запись новых файлов:**
   Новые файлы сохраняются сразу в R2 с ключом `users/{userId}/{UUID}_{fileName}`. В PostgreSQL записываются метаданные (`storage_provider = 'S3'`, `s3_key = ...`), а поле `content BYTEA` остается `NULL`.
2. **Чтение старых файлов (Обратная совместимость):**
   При запросе файла проверяется флаг `storage_provider`. Если он равен `'DATABASE'` или `NULL`, файл отдается из массива байтов в PostgreSQL. Если равен `'S3'`, инициируется чтение из R2 (`s3Client.getObject(...)`).
3. **Ленивый дренаж (Background Data Drain):**
   Фоновый ночной процесс порциями переносит старые файлы из PostgreSQL в R2, выставляет `storage_provider = 'S3'`, сохраняет `s3_key` и зануляет `content = NULL`. Затем однократный `VACUUM FULL stored_files` освобождает дисковое пространство СУБД.

## 4. Безопасность и Best Practices

1. **Защита памяти JVM (Zero-Copy Streaming):**
   Никогда не аллоцировать `byte[]` для входящих файлов в контроллере. Использовать `InputStream` и передавать его напрямую в `s3Client.putObject(..., RequestBody.fromInputStream(inputStream, contentLength))`.
2. **Сетевые таймауты SDK:**
   В `S3Config` обязательно задавать явные таймауты сокета (connectTimeout 5s, socketTimeout 30s), чтобы временные сбои на пограничных маршрутизаторах Cloudflare не вызывали зависание пула потоков Tomcat.
3. **Presigned URLs для больших файлов:**
   Для медиафайлов LMS и больших ZIP-архивов генерировать временные Pre-signed GET ссылки со сроком жизни 15 минут, передавая нагрузку по отдаче трафика глобальной CDN-сети Cloudflare.
