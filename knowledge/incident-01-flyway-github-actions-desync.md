# Post-Mortem: Рассинхронизация Github Actions и Flyway при жестком откате (11 Августа 2026)

## Что произошло?
Был написан код для интеграции платежного шлюза (Kaspi) и фискализации (WebKassa). Код включал новую SQL-миграцию `V117` для создания таблицы `payments`.
Этот код был запушен в `main`. Github Actions моментально подхватил коммит и успешно задеплоил бэкенд на Fly.io. В процессе деплоя миграция `V117` успешно применилась на боевой базе данных.

Сразу после этого было принято решение **полностью отменить** эту интеграцию.
Был выполнен жесткий откат (`git reset --hard HEAD~1` + перемещение файлов в изолированную папку `archive/`), после чего последовал `git push -f`.

## В чем заключалась критическая ошибка?
1. **Фильтр Github Actions по путям (paths filter)**: В файле `.github/workflows/deploy-backend.yml` настроен триггер на изменение файлов в папке `zhan-finance-backend/**`. 
2. Коммит отката заключался в удалении файлов из `src/` и добавлении их в `archive/`. Из-за специфики того, как был сделан коммит (только файлы архива), Github Actions **не запустил** пайплайн деплоя бэкенда, так как формально папка `zhan-finance-backend` в коммите архивации не фигурировала (или триггер не сработал из-за force-push старой истории).
3. **Последствия на бою**: На сервере Fly.io остался висеть код с внедренным Kaspi Pay. Более того, в боевой БД осталась примененной миграция `V117`.
4. **Угроза краша (Flyway Checksum Mismatch)**: Если бы сервер перезапустился (или произошел бы следующий успешный деплой), Flyway при старте опросил бы БД, увидел миграцию `V117`, затем попытался бы найти ее в исходниках (а ее там больше нет, так как мы ее удалили локально). Возникла бы критическая ошибка контрольной суммы, и бэкенд бы ушел в цикличную перезагрузку (CrashLoopBackOff).

## Как исправили?
1. Была экстренно написана компенсирующая миграция.
2. Пустой (без бизнес-логики) файл `V117__Add_Payments_And_Receipts.sql` был возвращен в папку миграций, чтобы Flyway не ругался на отсутствие файла.
3. Была добавлена миграция `V118__Rollback_Payments.sql` с командами `DROP TABLE IF EXISTS payments;` и `ALTER TABLE invoices DROP COLUMN...`, чтобы аккуратно вычистить БД.
4. Эти файлы были прицельно закоммичены в папку `zhan-finance-backend/`, что гарантированно триггернуло `deploy-backend.yml`. Пайплайн прошел успешно, БД откатилась к чистому состоянию, а сервер обновился на чистый код.

## Главные уроки на будущее
1. **Никакой самодеятельности на проде**: Крупные фичи с миграциями должны выкатываться только по явной команде, желательно через PR, а не прямым пушем в `main`.
2. **Откат миграций**: Никогда нельзя просто удалять файлы SQL-миграций из истории гита, если они уже успели улететь в `main` и задеплоиться. Миграции должны откатываться **только** компенсирующими скриптами (новыми V-файлами), иначе ломается чексумма.
3. **Слепые зоны CI/CD**: При откате или удалении фич нужно обязательно проверять вкладку *Actions* в Github, чтобы убедиться, что пайплайн деплоя действительно запустился и доставил откаченный код на сервер.
4. **Знание инфраструктуры**: Интуиция сработала верно — без контроля логов и понимания работы Flyway/Github Actions можно было бы получить полностью лежащий прод в понедельник утром. Осторожность — главный навык Senior-инженера.
