# Архитектура Памяти JVM: Metaspace, Динамические Прокси и Бюджетирование в Контейнерах

## 1. Введение и Проблематика
В микросервисных и контейнеризованных развертываниях (Fly.io, Docker, Kubernetes) с жесткими лимитами оперативной памяти (например, 512MB RAM) разработчики часто фокусируются исключительно на размере кучи (Heap, `-Xmx`).
Однако в современных enterprise-приложениях на **Java 17 / Spring Boot 3+** критическую роль играет non-heap память, в частности **Metaspace**.

Непонимание природы Metaspace приводит к двум крайностям:
1. **False-Positive Alarms**: Паника дежурного инженера из-за алерта о заполнении Metaspace до 126MB при лимите в 128m.
2. **Silent OOM Crashes**: Внезапное падение контейнера с кодом `java.lang.OutOfMemoryError: Metaspace` при подключении нового доменного модуля, компиляции шаблонов (Thymeleaf/JasperReports) или ротации классов.

---

## 2. Анатомия Metaspace в Java 17

С Java 8 область Permanent Generation (PermGen) была удалена, и метаданные классов были вынесены в **Metaspace** — область нативной памяти операционной системы.

В Metaspace размещаются:
- **Klass Metaspace**: Метаданные загруженных классов (структура полей, методов, аннотаций, интерфейсов).
- **Constant Pool**: Таблицы констант классов, ссылки на методы и поля, литералы.
- **Method Bytecode**: Байткод всех методов классов приложения и сторонних библиотек.
- **Dynamic Proxies & Generated Classes**: Байткод классов, сгенерированных на лету фреймворками во время работы приложения.

## 3. Факторы Взрывного Роста Metaspace в Spring Boot

Spring Boot активно использует генерацию классов во время исполнения (Runtime Code Generation). При первом обращении к функционалу происходит резкий скачок выделения страниц памяти Metaspace:

### 3.1. CGLIB и ByteBuddy Прокси
Spring создает динамические подклассы для реализации сквозной функциональности (AOP):
- `@Transactional`: Оборачивает методы сервисов в транзакционные интерцепторы.
- `@PreAuthorize` / `@Secured`: Создает интерцепторы безопасности для проверки ролей (`ADMIN`, `EMPLOYEE`, `ADVISOR`).
- `@Async` и `@EventListener`: Генерирует прокси для асинхронного выполнения задач через `TaskExecutor`.
- Spring Data JPA: Создает динамические классы реализации для каждого интерфейса `*Repository`.

### 3.2. Hibernate и ORM Рефлексия
Hibernate генерирует кастомные аксессоры сущностей (fast class accessors), скомпилированные структуры запросов HQL/JPQL и прокси для ленивой загрузки (`LazyLoadingProxy`).

### 3.3. Шаблонизаторы и Сериализаторы
- **Jackson (JSON)**: Генерирует динамические сериализаторы и десериализаторы для DTO при первом вызове эндпоинта.
- **Thymeleaf / OpenHtmlToPdf**: Компилирует HTML-шаблоны и шрифтовые таблицы Cyrillic/TrueType в структуры памяти.

## 4. Эффект «Плато» (Metaspace Plateau)

Важнейшее свойство Metaspace: **память растет ступенчато во время прогрева (warmup) и выходит на плато**.

```
Metaspace (MB)
  ^
160|                                   ================ (Плато: ~130-150MB)
120|                         /---------
 80|               /---------
 40|     /---------
  0+-----+---------+---------+---------+------------------> Время / Запросы
     Старт      Auth/CRM    Invoices/PDF    Стабильный прод
```

- При старте приложения подгружаются только базовые классы Spring Context (~60-80 MB).
- При первом сквозном прогоне (нагрузочные или E2E тесты) вызываются все ветки кода, и Metaspace подскакивает до **120-140 MB**.
- После завершения прогрева **новые классы больше не загружаются**, и Metaspace стабилизируется.

## 5. Бюджетирование Памяти Контейнера 512MB RAM

В контейнере с лимитом 512MB RAM суммарное потребление памяти складывается из:

$$\text{Total Memory} = \text{Heap} + \text{Metaspace} + \text{Thread Stacks} + \text{Direct Buffers} + \text{JVM Overhead}$$

| Компонент | Параметр JVM | Рекомендуемый размер (512MB VM) | Описание |
| :--- | :--- | :--- | :--- |
| **Java Heap** | `-Xmx256m -Xms128m` | **256 MB** | Бизнес-объекты, кэши Caffeine, DTO |
| **Metaspace** | `-XX:MaxMetaspaceSize=256m` | **256 MB** | Метаданные классов, AOP-прокси, Jackson |
| **Thread Stacks** | `-Xss512k` | **30 MB** (60 потоков × 512KB) | Стеки вызовов потоков Tomcat и пулов |
| **Direct Buffers & Netty** | `-XX:MaxDirectMemorySize=32m` | **32 MB** | Буферы ввода-вывода HTTP/WebSocket |
| **JVM Engine & GC** | Нативная память | **~30-40 MB** | Внутренние структуры JVM и G1/Serial GC |

*Примечание:* Параметр `-XX:MaxMetaspaceSize=256m` задает **верхнюю границу**, а не сразу резервирует всю память. Фактическое потребление после прогрева составляет ~125-140 MB.

```toml
[env]
  SERVER_ADDRESS = "0.0.0.0"
  SERVER_PORT = "8080"
  SPRING_PROFILES_ACTIVE = "prod"
  JAVA_TOOL_OPTIONS = "-XX:MaxMetaspaceSize=256m"
```

## 7. Калибровка Мониторинга и Алертинга (Prometheus / Grafana)

Ошибочный подход: ставить статический алерт на 120MB, если для приложения с 20 модулями 125MB — это нормальное рабочее плато.

### Правильное правило алерта в Prometheus Alertmanager:
```yaml
- alert: MetaspaceNearLimit
  expr: (jvm_memory_used_bytes{id="Metaspace"} / jvm_memory_max_bytes{id="Metaspace"}) > 0.85
  for: 5m
  labels:
    severity: warning
  annotations:
    summary: "JVM Metaspace utilization exceeds 85% on {{ $labels.instance }}"
    description: "Metaspace used: {{ $value | humanizePercentage }} of allocated limit."
```
- Алерт реагирует на **процент заполнения (>85%)**, а не на абсолютное число.
- Задержка `for: 5m` предотвращает ложные срабатывания при всплеске во время холодного старта.
