# JVM Metaspace Tuning для небольших контейнеров (512MB RAM)

## Контекст проблемы
В проекте [[jf-1c]] (Spring Boot 3, PostgreSQL, Flyway) на хостинге Fly.io с 512MB RAM сервер начал приближаться к лимиту Metaspace (128MB). В `fly.toml` стоял параметр `-XX:MaxMetaspaceSize=256m`.

## Ошибка конфигурации
Устанавливать `MaxMetaspaceSize=256m` на машине с 512MB RAM — это гарантированный OOM (Out Of Memory) от Linux (OOM Killer).
Spring Boot 3 требует около 80-120MB Metaspace для работы (Hibernate, CGLIB прокси, Thymeleaf и рефлексия). 

Если Metaspace разрастется до 256MB, а Heap (куча) заберет еще ~128-256MB по дефолту, сумма (включая нативные потоки, стек и Code Cache) превысит 512MB, и контейнер будет принудительно убит операционной системой.

## Правильное решение (Броня для 512MB RAM)

Для монолита на Java 17+ в контейнере 512MB необходимо жестко ограничить все области памяти JVM:

```toml
JAVA_TOOL_OPTIONS = "-Xmx256m -Xms256m -XX:MaxMetaspaceSize=144m -Xss512k -XX:ReservedCodeCacheSize=64m -XX:+UseG1GC"
```

### Разбор параметров:
1. `-Xmx256m -Xms256m`: Жестко фиксируем кучу. Никаких плавающих аллокаций.
2. `-XX:MaxMetaspaceSize=144m`: Оставляем текущие 128MB + небольшой запас для генерации прокси в рантайме. Не даем сожрать больше.
3. `-Xss512k`: Уменьшаем размер стека потоков с 1MB (дефолт) до 512KB. Это экономит десятки мегабайт, особенно при большом количестве WebSocket-соединений (как в модуле chat в [[jf-1c]]).
4. `-XX:ReservedCodeCacheSize=64m`: Ограничиваем кеш JIT-компилятора (по дефолту он 240MB, что избыточно).
5. `-XX:+UseG1GC`: Используем G1 сборщик мусора (по дефолту в Java 17+, но лучше указать явно).
