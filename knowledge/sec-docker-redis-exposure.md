# Security: Защита внутренних сервисов в Docker и частые уязвимости

## Проблема 1: Открытый Redis (без пароля, порт наружу)
По умолчанию официальный образ `redis` не требует пароля. В конфигурациях `docker-compose.yml` разработчики часто пишут `ports: - "6379:6379"`. Docker по умолчанию проксирует такие порты на `0.0.0.0` (все сетевые интерфейсы хоста). Если на production-сервере нет строгого firewall, Redis становится доступен всему интернету. Это позволяет злоумышленникам читать кэш, перехватывать сессии и refresh токены, а также изменять данные.

### Правильное решение
1. **Никаких публичных портов для внутренних сервисов**. Базы данных и кэш должны общаться с бекендом только через внутреннюю сеть Docker. Если порт нужен для локальной отладки (DBeaver, RedisInsight), биндить его **строго на localhost**: `127.0.0.1:6379:6379`.
2. **Пароль обязателен**. Всегда использовать `--requirepass` для Redis, даже внутри защищенной сети.

```yaml
# Пример безопасной конфигурации
redis:
  image: redis:alpine
  command: redis-server --requirepass ${REDIS_PASSWORD}
  ports:
    - "127.0.0.1:6379:6379" # Доступ только с localhost хост-машины
```

## Проблема 2: IDOR (Insecure Direct Object Reference)
IDOR возникает, когда API принимает идентификатор объекта (например, `/v1/experience/{id}`), и бекенд возвращает или модифицирует этот объект без проверки того, принадлежит ли он текущему пользователю. 

### Правильное решение (Spring Boot)
Каждое обращение к объекту по ID (в CRUD операциях) обязано сопровождаться проверкой владельца (ownership check) перед выполнением бизнес-логики:
```java
Experience exp = experienceRepository.findById(id).orElseThrow(() -> new NotFoundException());
if (!exp.getProfile().getId().equals(SecurityUtils.getCurrentUserId())) {
    throw new ForbiddenException("Access denied");
}
```

## Проблема 3: Уязвимости env() вне конфигов
В экосистеме PHP/Laravel вызов функции `env()` напрямую в коде (вне конфиг-файлов) является критической ошибкой, так как после выполнения `php artisan config:cache` переменные окружения больше не читаются из `.env` файла, и `env()` начинает возвращать `null`. На этом часто ломаются интеграции с платежками.

### Ситуация в других стеках:
- **Spring Boot**: Проблемы с `env()` нет. Переменные читаются через аннотацию `@Value("${key}")` или класс `Environment`, а значения надежно инжектятся на этапе старта приложения.
- **Vite / React**: Переменные `import.meta.env` вшиваются в итоговый JS-бандл (static replace) на этапе билда (за исключением переменных без префикса `VITE_`, которые туда вообще не попадут). Это безопасно и не подвержено рантайм-сбоям.
