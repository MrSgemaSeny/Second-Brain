## Блок 1: Сетевой слой, API и коммуникация

### 1. Ограничение частоты запросов (Rate Limiting)
- **Слепая зона вайб-кодера**: Модели пишут эндпоинты без учета нагрузки. Любой спам-скрипт или зацикленный фронтенд кладет базу данных.
- **Инженерный стандарт**: Алгоритмы Token Bucket / Leaky Bucket (Bucket4j, Redis sliding window). Разделение лимитов по уровням: неавторизованные запросы по IP (10/мин), пользовательские запросы (100/мин), ресурсоемкие экспортные операции (5-10/мин). Учет заголовков обратного прокси (`Fly-Client-IP`, `X-Forwarded-For`) для исключения обхода через спуфинг IP.

### 2. Кэширование и обратные прокси (Caching & Reverse Proxies)
- **Слепая зона вайб-кодера**: Каждый запрос заставляет бэкенд вызывать тяжелые SQL-запросы или внешние API.
- **Инженерный стандарт**: Двухуровневое кэширование: L1 (in-memory Caffeine per-process) для микросекундного доступа и L2 (Redis / Memcached) для разделяемого состояния между подами. Конфигурация Nginx / Envoy / Cloudflare для отдачи статики и агрессивного кэширования публичных GET-эндпоинтов с `Cache-Control: public, max-age=...`.

### 3. Балансировка нагрузки и Service Discovery
- **Слепая зона вайб-кодера**: Приложение считается единственным монолитом, запущенным на localhost:8080.
- **Инженерный стандарт**: Stateless-архитектура без хранения сессий на диске сервера. Использование L4 (TCP) и L7 (HTTP/gRPC) балансировщиков (AWS ALB, Traefik, Kubernetes Ingress) с алгоритмами Round-Robin, Least Connections. Service Discovery (Consul, CoreDNS в k8s) для автоматической маршрутизации трафика на здоровые реплики.

### 4. Circuit Breakers, Таймауты и Retries
- **Слепая зона вайб-кодера**: Вызов внешнего сервиса (WebKassa, Kaspi, OpenAI) без таймаута подвешивает поток сервлета (Tomcat thread pool exhaustion). При сбое код сразу падает или бесконечно долбит упавший сервис в цикле.
- **Инженерный стандарт**: Паттерн Circuit Breaker (Resilience4j). Жесткие таймауты (connect-timeout: 3s, read-timeout: 5s). Повторные запросы (Retries) исключительно с экспоненциальной задержкой (Exponential Backoff) и рандомизацией интервала (Full Jitter), чтобы предотвратить Thundering Herd Problem.

### 5. Идемпотентность (Idempotency)
- **Слепая зона вайб-кодера**: Повторное нажатие кнопки пользователем или повтор сетевого пакета списывает деньги дважды или дублирует заказ.
- **Инженерный стандарт**: Заголовок `Idempotency-Key` (UUIDv4) на всех мутирующих запросах (POST/PUT). Бэкенд сохраняет ключ в Redis/Postgres с блокировкой на время обработки и возвращает закэшированный ответ при дубликатах.

### 6. Очереди сообщений, Pub/Sub и Dead Letter Queues (DLQ)
- **Слепая зона вайб-кодера**: Отправка email, генерация PDF и нотификации выполняются синхронно в теле HTTP-запроса клиента.
- **Инженерный стандарт**: Асинхронные брокеры (RabbitMQ, Apache Kafka, AWS SQS). Разделение задач на очереди обработки. Паттерн Dead Letter Queue (DLQ) для сообщений, упавших с ошибкой N раз, с алертом в Sentry/Telegram и возможностью ручного ретрая (Replay).

### 7. Распределенные транзакции и паттерн Saga
- **Слепая зона вайб-кодера**: Попытка повесить `@Transactional` поверх трех разных микросервисов или внешних API. При падении второго шага база откатывается, а деньги во внешнем банке уже списаны.
- **Инженерный стандарт**: Паттерн Saga (Choreography или Orchestration). Каждый шаг выполняет локальную транзакцию и генерирует событие. В случае сбоя запускаются компенсирующие транзакции (Compensating Transactions: отмена бронирования, возврат средств).

## Блок 2: Реальтайм, Concurrency и Управление памятью

### 8. Реальтайм-транспорт: WebSockets vs SSE vs Long Polling
- **Слепая зона вайб-кодера**: Подключение WebSocket ради простого пуша уведомлений раз в час, либо опрос сервера (Long Polling) раз в 500 мс с созданием огромного оверхеда.
- **Инженерный стандарт**:
  - WebSockets (STOMP): Двусторонний полнодуплексный обмен с низкой задержкой (чаты, онлайн-доски, трейдинг).
  - Server-Sent Events (SSE): Однонаправленный стриминг от сервера к клиенту поверх стандартного HTTP (LLM токен-стриминг, уведомления, дашборды).
  - Long Polling: Устаревший fallback для сред с блокировкой сокетов.

### 9. Индексация баз данных и оптимизация запросов
- **Слепая зона вайб-кодера**: Написание простых JPA-запросов (`findByUserIdAndStatus`), которые делают Full Table Scan (Seq Scan) на таблицах с миллионами строк.
- **Инженерный стандарт**: Составные индексы (B-Tree) с соблюдением порядка селективности (Equality -> Range). Использование Covering Indexes. Анализ через `EXPLAIN (ANALYZE, BUFFERS)`. Партиционирование больших таблиц истории (Audit, Chat) по датам.

### 10. Проблема N+1 запросов
- **Слепая зона вайб-кодера**: Ленивая загрузка связей (`FetchType.LAZY` / relations в TypeORM). Рендеринг списка из 100 курсов порождает 101 SQL-запрос к БД, исчерпывая пул соединений.
- **Инженерный стандарт**: Использование `JOIN FETCH` в JPQL, Entity Graphs (`@EntityGraph`), либо `DataLoader` в GraphQL. Строгий мониторинг количества запросов на запрос через DataSource-прокси (vladmihalcea db-util).

### 11. Пулы соединений (Connection Pools)
- **Слепая зона вайб-кодера**: Дефолтные настройки HikariCP (maximum-pool-size: 100) на слабой машине с 512MB RAM, приводящие к падению Postgres по памяти.
- **Инженерный стандарт**: Расчет пула по формуле: `connections = ((core_count * 2) + effective_spindle_count)`. Настройка `connection-timeout: 30000`, `max-lifetime: 600000`, `leak-detection-threshold: 2000`. Вынесение долгоживущих задач из транзакций.

### 12. CAP-теорема и Eventual Consistency
- **Слепая зона вайб-кодера**: Ожидание мгновенной согласованности данных в распределенной системе (например, чтение сразу после записи из реплики для чтения).
- **Инженерный стандарт**: Осознанный выбор между CP (Consistency + Partition Tolerance) и AP (Availability + Partition Tolerance). Архитектура под слабую/конечную согласованность (Eventual Consistency): оптимистичные апдейты на клиенте, сопоставление версий, обработка конфликтов на бэкенде.

### 13. Блокировки и Race Conditions: Оптимистические vs Пессимистические
- **Слепая зона вайб-кодера**: Код `val balance = getBalance(); setBalance(balance - amount);` в многопоточной среде приводит к списанию ниже нуля при одновременных кликах.
- **Инженерный стандарт**:
  - Оптимистическая блокировка (`@Version`): Для систем с низкой вероятностью коллизий (редактирование профиля).
  - Пессимистическая блокировка (`SELECT FOR UPDATE`): Для критических финансовых операций с высокой конкурентностью.
  - Распределенная блокировка (Redlock через Redis / etcd): Для координации между несколькими инстансами сервиса.

### 14. Deadlocks, Утечки памяти и Thread Safety
- **Слепая зона вайб-кодера**: Использование обычного `HashMap` вместо `ConcurrentHashMap`, сохранение объектов в статических полях или `ThreadLocal` без вызова `remove()`.
- **Инженерный стандарт**: Защита от дедлоков через единый строгий порядок захвата ресурсов (Order-based resource acquisition). Очистка контекстов `ThreadLocal` в `finally`-блоках фильтров сервлетов. Профилирование памяти (JProfiler, Eclipse Memory Analyzer, heap dumps) для выявления утечек объектов.

### 15. Backpressure и защита от переполнения
- **Слепая зона вайб-кодера**: Сервер считывает файл или поток сообщений целиком в память, вызывая `OutOfMemoryError` (OOM).
- **Инженерный стандарт**: Реактивные стримы (Reactive Streams / Project Reactor / WebFlux), потоковая обработка через каналы (Channels / Pipelines). Клиент сигнализирует серверу, сколько данных он готов принять (Demand signalling).
