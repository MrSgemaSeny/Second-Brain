# Проблема: Продакшен упал / Инцидент / Плановое обслуживание
## Контекст (когда возникает)
Универсальный Runbook для проектов, задеплоенных по стеку: **Бэкенд на Fly.io (Spring Boot) + PostgreSQL + Фронтенд на GitHub Pages (React)**. Актуально для JF-1C и MeDev.

## Решение (Runbook)

### 1. Что делать, если бэкенд упал (Fly.io)

1. **Проверь статус инстансов и логи:**
   ```bash
   # Посмотреть общую картину
   flyctl status --app <имя_приложения>
   
   # Посмотреть живые логи бэкенда (ищем Exceptions или OOM)
   flyctl logs --app <имя_приложения>
   ```

2. **Жесткая перезагрузка (если зависло наглухо):**
   ```bash
   flyctl apps restart <имя_приложения>
   ```

3. **Откат к стабильной версии (если релиз сломал прод):**
   ```bash
   # Смотрим историю релизов
   flyctl releases list --app <имя_приложения>
   
   # Откатываем на конкретную стабильную версию (например, v12)
   flyctl releases rollback v12 --app <имя_приложения>
   ```

### 2. Как накатить обновление

1. **Убедись, что локальные тесты проходят (зеленые).**
2. Закоммить изменения и запушь в ветку `main`:
   ```bash
   git add .
   git commit -m "feat: [описание]"
   git push origin main
   ```
3. Открой вкладку **Actions** в GitHub репозитории.
   - Пайплайн `deploy-backend.yml` автоматически соберет Docker-образ и отправит его на Fly.io.
   - Пайплайн `ci.yml` (или аналогичный) соберет статику Vite и опубликует на GitHub Pages.
4. **Проверь успешность:** Если в Telegram пришло уведомление от бота (настроено для JF-1C), значит деплой прошел успешно.

### 3. Как восстановить из бэкапа (PostgreSQL)

Если база данных повреждена (случайный DROP, баг в логике):

1. **Где взять бэкап:**
   - Бэкапы автоматически создаются GitHub Actions-воркером и могут сохраняться как артефакты в Actions, либо отправляться на R2/Telegram (в зависимости от настроек проекта). Скачай последний рабочий дамп (файл `.dump` или `.sql`).

2. **Как восстановить в продакшен (на Fly.io):**
   ```bash
   # Открываем туннель к БД на локальный порт 5432
   flyctl proxy 5432:5432 -a <название_приложения_db>
   
   # В другом терминале восстанавливаем дамп через pg_restore (если формат custom/dump)
   pg_restore -h localhost -p 5432 -U postgres -d <имя_базы> --clean <путь_к_файлу.dump>
   
   # Или если это простой SQL скрипт:
   psql -h localhost -p 5432 -U postgres -d <имя_базы> -f <путь_к_файлу.sql>
   ```

3. **Как восстановить локально (для разбора инцидента):**
   ```bash
   pg_restore -h localhost -p 5432 -U postgres -d <локальная_база> --clean <путь_к_файлу.dump>
   ```

### 4. Что делать, если фронтенд отвалился (GitHub Pages)

1. **Проверь Actions сборки:** Возможно, сборка упала из-за ошибки типов TypeScript (`npm run build` свалился).
2. **Очистка кэша:** GitHub Pages может агрессивно кэшировать старые JS-чанки. Если пользователи жалуются на пустой экран, попроси их обновить страницу с очисткой кэша (`Ctrl + F5` / `Cmd + Shift + R`).
3. **Откат фронтенда:** На GitHub Pages нельзя откатить релиз одной кнопкой. Решение: локально сделать `git revert` сломанного коммита и заново запушить в `main`.

## Почему не Y (альтернативы которые не подошли)
- **Почему не прямые подключения к БД без proxy?** Безопасность. PostgreSQL на Fly.io спрятан за приватной сетью IPv6. Выставлять порт наружу для бэкапов опасно. `flyctl proxy` — единственный правильный путь.
- **Почему не ручной деплой с ноутбука?** Если интернет отвалится во время пуша слоя Docker, приложение может зависнуть в деплое. GitHub Actions гарантирует стабильный канал и воспроизводимость сборки.
