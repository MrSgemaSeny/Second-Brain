# Защита загрузки файлов (Magic Bytes Validation)

## Суть проблемы
Полагаться только на расширение файла (`.pdf`) или на заголовок `Content-Type` из HTTP-запроса при загрузке файлов категорически нельзя. Злоумышленник может перехватить запрос и отправить исполняемый файл или вредоносный бинарник под видом `application/pdf`.

Парсеры файлов (например, `PDFBox`, `Apache POI`, `ImageIO`) при попытке распарсить вредоносный или специально сгенерированный бинарник могут:
- Уйти в бесконечный цикл (100% CPU).
- Спровоцировать OutOfMemoryError (OOM), пытаясь аллоцировать память под огромный "размер", указанный в битом заголовке.
- Выполнить RCE (если в библиотеке парсера есть CVE).

## Как чинить (Magic Bytes)
Каждый тип файла имеет сигнатуру — несколько фиксированных байтов в самом начале файла (Magic Bytes).
Для PDF первые 4 байта всегда равны `%PDF` (в ASCII: `37 50 44 46`).

Перед передачей потока или байтового массива в парсер, нужно вручную (или через библиотеку Apache Tika) прочитать первые байты и сверить их с сигнатурой. Это быстрая (O(1)) и дешевая операция, которая отсекает 99% мусора до того, как тяжелый парсер начнет работу.

### Паттерн (Java, валидация PDF):
```java
byte[] fileBytes = file.getBytes();
if (fileBytes.length < 4 || 
    fileBytes[0] != '%' || 
    fileBytes[1] != 'P' || 
    fileBytes[2] != 'D' || 
    fileBytes[3] != 'F') {
    throw new IllegalArgumentException("Invalid PDF magic bytes");
}
// Только теперь можно безопасно(относительно) передавать в PDFBox
PDDocument document = Loader.loadPDF(fileBytes);
```

## Когда применять
Абсолютно при любой загрузке файлов (картинки, документы, архивы), которая впоследствии будет парситься или процесситься на бэкенде. Для сложных проверок (где много форматов) лучше использовать `Apache Tika`.
