# Архитектурный паттерн: AI Structured JSON Generation

## Проблема
Современные приложения общаются с ИИ не просто текстом, а строгими объектами данных (DTO). LLM по умолчанию выдает текст, который может содержать разметку Markdown (````json ... ````) или комментарии, из-за чего стандартные парсеры (например, `ObjectMapper` в Java) падают с ошибками.

## Решение: Принудительная JSON-генерация

### 1. Настройка System Prompt
Системный промпт должен не просто просить JSON, а категорически запрещать любую другую выдачу.
Пример идеального промпта:
> "Ты — API сервер. Твоя единственная задача — вернуть строго валидный JSON. НИКАКИХ комментариев, НИКАКОГО markdown (не используй ```json). ТОЛЬКО сырой JSON. Если ты вернешь хоть одно слово кроме JSON, система сломается. Структура: { "field1": "value" }"

### 2. Поддержка JSON Mode (Groq / OpenAI)
Если провайдер (как Groq) поддерживает параметр `response_format: { type: "json_object" }`, его **обязательно** нужно использовать. Это на уровне API заставляет модель гарантировать валидность структуры.

### 3. Graceful Degradation (Обработка ошибок парсинга)
Несмотря на все защиты, LLM может ошибиться. В бэкенде должен быть реализован отказоустойчивый парсер.
Например:
- Использование регулярных выражений для "вырезания" JSON из текста, если модель все-таки добавила markdown.
- `try-catch` вокруг `objectMapper.readValue`.
- Механизм **Retry** (например, `Resilience4j`), который повторит запрос к LLM в случае неудачного парсинга.

### 4. Вложенные коллекции (Nested Entities)
При проектировании DTO для LLM, все вложенные коллекции (опыт работы, проекты) должны быть четко типизированы массивами. Spring должен понимать, как их десериализовать.

## Пример из MeDev (AiAnalysisService)
В MeDev `GroqClient` и `AiAnalysisService` работают в связке. ИИ анализирует исходные данные (PDF + GitHub) и возвращает огромный, сложно-вложенный `ProfileDto` (с проектами, скиллами, опытом). За счет строгого промптинга и включенного `json_object`, парсинг происходит в 99.9% случаев без ошибок.
