# От MVP к Production: Чек-лист безопасности и типичные компромиссы

При переходе SaaS-проекта из стадии "работающего прототипа" (MVP) в стадию "production-ready" (работа с реальными клиентами и данными) технический долг, накопленный ради скорости запуска, превращается в критические уязвимости. 
Ниже описан свод знаний, собранный на основе секьюрити-ревью боевого бэкенда (на примере Spring Boot + React + Fly.io).

## Философия «Make it work» vs «Make it secure»
Во время разработки MVP мы идем на компромиссы. Наша цель — быстро интегрировать фичи, не тратя недели на отладку CORS или настройку сложных Security-цепочек. Однако, когда проект деплоится на облачные платформы (например, Fly.io) и принимает реальных юзеров, эти компромиссы становятся недопустимыми.

## Топ критичных "дыр" MVP и как их превратить в Prod-стандарт

### 1. Отключение строгой защиты кук (CSRF & SameSite)
**Как было в MVP:** 
Из-за того, что фронтенд (Github Pages) и бэкенд (Fly.io) лежат на разных доменах, авторизационные куки помечаются как `SameSite=None` (иначе браузер их блокирует). Чтобы "не париться" с CSRF токенами, встраивается кастомный фильтр, пропускающий запросы с `Content-Type: application/json`.
**Почему это уязвимость в Prod:**
- `SameSite=None` разрешает отправку кук на кросс-доменные запросы.
- `Content-Type: application/json` больше не является надежной защитой от CSRF (особенно с использованием `no-cors` mode в fetch или уязвимостей локального CORS `localhost:*`).
**Prod-Решение:**
Если нет возможности разместить фронт и бэк на одном домене (чтобы использовать `SameSite=Lax`), необходимо внедрять классический `CookieCsrfTokenRepository` (или Double Submit Cookie / Synchronizer Token Pattern). Фильтры по заголовкам можно использовать только как дополнительный эшелон защиты.

### 2. Хардкод секретов и дефолтные значения (`@Value`)
**Как было в MVP:**
Чтобы бэкенд локально не падал при отсутствии файла конфигурации, разработчики вшивают default значения для секретов: `@Value("${google.client.id:real-client-id-here}")`.
**Почему это уязвимость в Prod:**
Секреты навсегда оседают в истории Git. Если кто-то форкнет репозиторий или получит доступ к коду, секреты будут скомпрометированы.
**Prod-Решение:**
Fail-fast подход. Приложение **обязано** падать при запуске (CrashLoopBackOff), если критически важный env (токены, ключи, пароли) не предоставлен. `@Value("${google.client.id}")` — без дефолта.

### 3. Rate Limiting и спуфинг Client IP
**Как было в MVP:**
При деплое за балансировщик (Fly proxy, Nginx) реальный IP клиента скрывается за IP балансировщика. Разработчик читает `request.getHeader("Fly-Client-IP")` или `X-Forwarded-For`.
**Почему это уязвимость в Prod:**
Если порт приложения открыт "наружу" (или балансировщик не чистит заголовки), любой атакующий может подставить `Fly-Client-IP: 1.2.3.4` и обходить Rate Limit'ы, получая свежий пул лимитов на каждый запрос.
**Prod-Решение:**
- Закрыть прямой доступ к порту приложения (ingress routing).
- В Spring доверять прокси только через `ForwardedHeaderFilter` с жестко настроенным `server.tomcat.remoteip.internal-proxies` (доверенные IP балансировщиков).
- Если это невозможно гарантировать, надежнее использовать `request.getRemoteAddr()`.

### 4. JWT Токены в URL (WebSockets)
**Как было в MVP:**
Стандартный WebSocket API в браузере не умеет отправлять кастомные заголовки (типа `Authorization: Bearer`). Токен кидается в query parameter: `?token=eyJ...`.
**Почему это уязвимость в Prod:**
URL логируется везде: в логах балансировщика (Nginx, Fly), в истории браузера, в логах провайдера. Токен доступа утекает в открытый текст.
**Prod-Решение:**
Использовать протокол поверх WS (например, STOMP) и передавать токен внутри фрейма `CONNECT` в заголовках. Бэкенд должен вычитывать токен из `accessor.getFirstNativeHeader("Authorization")`. Fallback на query parameters необходимо полностью удалить.

### 5. Загрузка файлов без валидации содержимого (MIME/Magic Bytes)
**Как было в MVP:**
Чтобы быстро реализовать загрузку аватарок или вложений, бэкенд проверяет только расширение файла: `filename.endsWith(".pdf")` или слепо верит `Content-Type` из заголовка запроса.
**Почему это уязвимость в Prod:**
Злоумышленник может загрузить `.exe`, `.php` или shell-скрипт, назвав его `image.jpg`.
**Prod-Решение:**
Использовать Apache Tika для проверки **magic bytes** (сигнатуры самого файла на уровне байт). Плюс обязательно внедрить жесткие лимиты на размер файла на уровне контроллера и конфигурации `spring.servlet.multipart.max-file-size`.

### 6. Enumeration через публичные API (checkEmail)
**Как было в MVP:**
Для улучшения UX создается эндпоинт `/check-email`, который говорит: "такой юзер есть, он вошел через Google". 
**Почему это уязвимость в Prod:**
Злоумышленник может перебрать базу данных и составить список реальных email-адресов системы, а затем натравить на них credential stuffing (перебор паролей).
**Prod-Решение:**
Настроить жесткий Rate Limit (не более 5-10 запросов в минуту с одного IP). Если возможно — перестроить UX на "Magic Link" или стандартный флоу входа без подсказок о существовании пользователя ("Если этот email зарегистрирован, мы отправили письмо").

### 7. CSV Formula Injection
**Как было в MVP:**
Бэкенд генерирует CSV-выгрузку из базы, просто оборачивая строки в кавычки.
**Почему это уязвимость в Prod:**
Если пользователь ввел в поле "Имя" значение `=HYPERLINK("http://evil.com","Click")`, то при открытии CSV в Excel или LibreOffice формула будет выполнена (часто с запросом кредов или загрузкой малвари).
**Prod-Решение:**
Санитизация. Все строки, начинающиеся со знаков `=`, `+`, `-`, `@`, `\t`, `\r`, должны предваряться апострофом (`'`) или пробелом.

### 8. Race Conditions в логике выдачи токенов
**Как было в MVP:**
Сначала удаляется старый токен 2FA (`delete`), затем создается новый (`insert`).
**Почему это уязвимость в Prod:**
При параллельных запросах (concurrent requests) создается микро-окно, когда могут сгенерироваться и остаться валидными сразу два токена, что ломает логику безопасности.
**Prod-Решение:**
Использовать атомарные операции базы данных (upsert) или блокировки в Hibernate (`@Lock(LockModeType.PESSIMISTIC_WRITE)`).

---
## Резюме
Продакшен не прощает упрощений. Любой компромисс ради скорости разработки на старте должен быть зафиксирован в бэклоге (в виде Security-долга) и обязательно закрыт до начала активного маркетинга и привлечения реальных денег пользователей.
