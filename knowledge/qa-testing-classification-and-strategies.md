# Классификация и Стратегии Тестирования ПО (QA & Testing Taxonomy)

**Дата создания:** 2026-09-08  
**Статус:** Core Engineering Standard  
**Область:** Архитектура качества, Backend, Frontend, Безопасность, SRE  

Данный документ фиксирует полную таксономию видов тестирования, применяемую для обеспечения надежности, производительности и безопасности веб-платформ и SaaS-систем (JF-1C и смежные проекты).

---

## 1. Функциональные тесты (Functional Testing)

Функциональные тесты проверяют соответствие поведения системы бизнес-требованиям и спецификациям API на разных уровнях абстракции.

### 1.1. Unit-тестирование
- **Суть:** Проверка наименьших изолированных единиц кода — отдельных функций, классов или методов в полной изоляции.
- **Изоляция:** Все внешние зависимости (база данных, HTTP-клиенты, кэш, очереди сообщений) жестко подменяются моками (Mocks, Stubs).
- **Инструменты:** JUnit 5, Mockito, AssertJ (Java); Vitest, Jest (TypeScript/React).
- **Фокус:** Граничные условия, краевые случаи валидации, внутренняя бизнес-логика алгоритмов, расчет сумм и налогов.
- **Главные требования:** Высочайшая скорость выполнения (миллисекунды), детерминизм (zero flakiness), независимость от окружения.

### 1.2. Интеграционное тестирование (Integration Testing)
- **Суть:** Проверка совместной работы нескольких слоев приложения: `Controller -> Service -> Repository -> Data Access Layer`.
- **Окружение:** Запуск реального контекста приложения (Spring Boot Test) в связке с реальной или изолированной СУБД (PostgreSQL через Testcontainers или выделенную тестовую схему).
- **Инструменты:** `@SpringBootTest`, `@DataJpaTest`, `@AutoConfigureMockMvc`, Testcontainers, H2 (для простых тестов без вендор-специфичного SQL).
- **Фокус:** Корректность SQL-запросов и диалектов PostgreSQL, транзакционные границы (`@Transactional`, Rollback), маппинг сущностей JPA/Hibernate, валидация DTO через Bean Validation (`@Valid`), работа интерцепторов и фильтров.

### 1.3. Сквозное тестирование (End-to-End / E2E)
- **Суть:** Полная имитация пользовательского сценария от ввода данных в браузере или отправки внешнего HTTP-запроса через сетевой стек до фиксации изменений в базе данных и обратного ответа.
- **Инструменты:** Playwright, Cypress (Frontend E2E); RestAssured, WebTestClient (Backend API E2E).
- **Фокус:** Критические бизнес-цепочки: регистрация -> подтверждение email -> логин -> создание договора -> выставление инвойса -> проведение платежа -> скачивание PDF.
- **Особенности:** Дорогие в разработке и поддержке тесты. Запускаются на предрелизном этапе и в ночных прогонах CI/CD.

### 1.4. Контрактное тестирование (Contract Testing)
- **Суть:** Гарантия того, что поставщик API (Backend) и потребитель API (Frontend, мобильное приложение, смежный сервис) согласованы в схемах запросов и ответов.
- **Инструменты:** Pact, Spring Cloud Contract, OpenAPI Spec Validator (Swagger/OpenAPI 3.0 CLI).
- **Фокус:** Предотвращение ломающих изменений (Breaking Changes): переименование полей JSON, изменение типов данных, появление обязательных параметров без значений по умолчанию. Позволяет фронтенду и бэкенду разрабатываться независимо без риска рассинхронизации.

## 2. Нагрузочные тесты (Performance & Load Testing)

Нагрузочные тесты проверяют устойчивость сетевого стека, пула потоков веб-сервера, пулов соединений к базе данных и профиль потребления памяти под различными профилями нагрузки.

### 2.1. Smoke-тестирование нагрузки (Smoke Load)
- **Суть:** Минимальная базовая проверка жизнеспособности системы под минимальной нагрузкой (1-2 виртуальных пользователя, несколько секунд).
- **Цель:** Быстро подтвердить, что приложение развернуто корректно, базовые сетевые порты открыты, миграции применились, сервис отдает HTTP 200 на базовых healthcheck-маршрутах (`/actuator/health`, `/api/v1/auth/me`).

### 2.2. Тестирование под нагрузкой (Load Testing)
- **Суть:** Подача трафика, соответствующего ожидаемой рабочей нагрузке в пиковые часы реальной эксплуатации (например, 50-100 RPS на протяжении 10-30 минут).
- **Инструменты:** k6, Gatling, Apache JMeter, Locust.
- **Цель:** Измерение ключевых метрик SLA/SLO: задержка ответа (P90, P95, P99 Latency < 200-300 ms), процент ошибок (Error Rate < 0.1%), загрузка CPU и RAM хоста.

### 2.3. Стресс-тестирование (Stress Testing)
- **Суть:** Постепенное ступечатое наращивание нагрузки сверх нормативных показателей вплоть до достижения точки отказа (Breaking Point).
- **Цель:** Определение предела емкости системы и узких мест: исчерпание пула `HikariCP`, упирание в лимиты CPU, дисковые очереди ввода-вывода (IOPS).
- **Критерий успеха:** Graceful Degradation — система не должна зависать намертво; при перегрузке она должна корректно отдавать HTTP 429 или HTTP 503, а после снятия экстремальной нагрузки самостоятельно восстанавливать нормальную работоспособность без ручного перезапуска.

### 2.4. Спайк-тестирование (Spike Testing)
- **Суть:** Резкий кратковременный скачок нагрузки от фонового уровня до многократного пика за доли секунды (например, скачок с 5 RPS до 500 RPS) с последующим быстрым спадом.
- **Сценарий:** Эмуляция массовых рассылок (push, email), упоминания у крупных блогеров, внезапного наплыва пользователей при старте акций или подачи налоговой отчетности.
- **Фокус:** Поведение буферов очередей, реакция фильтров Rate Limiting (Bucket4j/Redis), масштабирование пулов соединений, отсутствие зависших Tomcat-потоков.

### 2.5. Тестирование на выносливость (Soak / Endurance Testing)
- **Суть:** Непрерывная подача умеренной нагрузки (например, 50-70% от максимума) на протяжении длительного времени (от 4-8 часов до нескольких суток).
- **Цель:** Выявление медленно накапливающихся проблем:
  - Утечки оперативной памяти в Java Heap (неразорванные ссылки, статические коллекции, кэши без TTL).
  - Утечки вне Heap-памяти (Metaspace, Direct Memory при работе с Netty/NIO).
  - Зависание и невозврат соединений в пул `HikariCP` (unclosed DB connections).
  - Переполнение дескрипторов файлов или сокетов операционной системы.

## 3. Тестирование безопасности (Security Testing)

Тестирование защищенности направлено на выявление уязвимостей, предотвращение утечки данных, проверку авторизационных барьеров и защиту инфраструктуры.

### 3.1. Динамическое сканирование уязвимостей (OWASP ZAP / Burp Suite)
- **Суть:** Автоматизированное и полуавтоматическое зондирование работающего приложения (DAST - Dynamic Application Security Testing).
- **Фокус:** Обнаружение инъекций (SQL Injection, Command Injection), межсайтового скриптинга (Reflected & Stored XSS), подделки межсайтовых запросов (CSRF), уязвимостей в заголовках безопасности (CORS, CSP, HSTS), ошибок конфигурации веб-сервера.

### 3.2. Тестирование обхода авторизации (Auth Bypass / Matrix Testing)
- **Суть:** Проверка ролевой модели (RBAC) и разграничения прав доступа на уровне объектов (ABAC / IDOR / BOLA).
- **Методика:** Составление матрицы доступа `[Роль x Эндпоинт]` и автоматический прогон всех запросов от лица каждой роли (ANONYMOUS, CLIENT, EMPLOYEE, LEARNER, CURATOR, ADVISOR, ADMIN).
- **Фокус:** 
  - Защита административных и мутирующих эндпоинтов от непривилегированных пользователей (HTTP 401/403).
  - Проверка владения ресурсом: предотвращение подстановки чужого `id` задачи, счета или документа (IDOR).
  - Защита от эскалации привилегий через манипуляцию полями в DTO при регистрации или обновлении профиля.

### 3.3. Тестирование лимитов частоты запросов (Rate Limit Testing)
- **Суть:** Проверка надежности работы троттлинга и фильтров ограничения частоты вызовов.
- **Алгоритмическое поведение (Sliding vs Fixed Window vs Token Bucket):**
  - *Fixed Window Boundary Burst:* Проверка поведения на стыке окон. При фиксированном окне (например, 60 req/min) клиент может послать 60 запросов в 12:00:59 и 60 в 12:01:01, вызвав двойную пиковую нагрузку. Тест должен проверять, сглаживает ли алгоритм всплески (Token Bucket в Bucket4j).
  - *Refill Strategy:* Тестирование дискретного (`refillIntervally`) против непрерывного (`refillGreedy`) пополнения токенов.
- **Тестирование защиты от подделки IP (X-Forwarded-For Spoofing):**
  - *Вектор атаки:* Атакующий генерирует каждый запрос с уникальным значением `X-Forwarded-For: random_ip` или `CF-Connecting-IP`. Если бэкенд наивно доверяет заголовку без проверки доверенных прокси, атакующий получает бесконечные новые корзины (Bucket) в кэше и 100% обходит Rate Limiter.
  - *Сценарий проверки:* Отправка серии запросов с одного TCP-сокета (`getRemoteAddr()`) с меняющимися заголовками `X-Forwarded-For` и `CF-Connecting-IP`. Тест обязан подтвердить, что до подключения CDN (Cloudflare) или при запросах мимо доверенной подсети лимитер группирует запросы по реальному сокетному адресу и блокирует клиента с кодом `HTTP 429`.
- **Проверяемые параметры:**
  - Корректная блокировка лишних запросов с кодом `HTTP 429 Too Many Requests`.
  - Наличие и корректность служебных заголовков (`Retry-After`, `X-Rate-Limit-Remaining`).
  - Пропуск `OPTIONS` запросов (CORS Pre-flight) без расходования токенов.

## 4. Регрессионные тесты (Regression Testing)

Регрессионные тесты гарантируют, что внесение новых фич, рефакторинг или исправление багов не ломают уже работающий функционал.

### 4.1. Снэпшот-тестирование (Snapshot Testing)
- **Суть:** Автоматическая фиксация структуры ответа или состояния компонента в виде эталонного файла-слепка (Snapshot).
- **Область применения:**
  - Frontend: рендеринг компонентов в Vitest/Jest (проверка, что разметка и классы Tailwind не изменились непреднамеренно).
  - Backend: фиксация комплексных JSON-ответов аналитики или генерации документов.
- **Поведение:** Тест падает при малейшем расхождении с эталоном. Разработчик обязан либо исправить регрессию, либо осознанно обновить снапшот (`--update-snapshot`).

### 4.2. Мутационное тестирование (Mutation Testing)
- **Суть:** Проверка качества и чувствительности самого набора тестов ("кто тестирует тесты?").
- **Методика:** Специальный инструмент вносит намеренные микро-изменения в байткод приложения (мутации): меняет `>` на `<=`, инвертирует булевы флаги, удаляет вызовы методов, подставляет `null`. Затем запускается существующий набор тестов.
- **Инструменты:** PITest (для Java), Stryker (для JavaScript/TypeScript).
- **Метрика:** Mutation Score (процент "убитых" мутантов). Если тесты прошли успешно при поврежденной бизнес-логике, значит, тесты формальны (высокий Code Coverage, но нулевая эффективность проверок).

## 5. Специфичные тесты (Architecture & Infrastructure Specific)

Тесты, ориентированные на специфические компоненты стека, работу с состоянием базы данных, реалтайм-протоколы и распределенные кэши.

### 5.1. Тестирование миграций Flyway (Migration Verification)
- **Суть:** Валидация всей цепочки SQL-миграций от `V1` до текущей версии на чистой временной базе данных.
- **Проверяемые риски:**
  - Отсутствие синтаксических ошибок в DDL/DML скриптах.
  - Целостность внешних ключей и ограничений (NOT NULL, UNIQUE, DEFAULT).
  - Неизменяемость контрольных сумм примененных миграций (Checksum Verification).
  - Корректность создания системных триггеров, процедур и индексов.
- **Правило:** В CI/CD пайплайне миграции обязаны подниматься на чистом контейнере PostgreSQL перед прогоном функциональных тестов.

### 5.2. Тестирование инвалидации кэша и протухания TTL (Cache Invalidation & TTL Expiry)
- **Суть:** Проверка консистентности данных между оперативной памятью кэша (Caffeine, Redis) и постоянным хранилищем (PostgreSQL).
- **Два источника Stale Data:**
  1. *Мутации без инвалидации:* Обновление или удаление сущности в обход `@CacheEvict` (прямой SQL, смежные сервисы).
  2. *Истечение TTL:* Запись должна быть удалена по таймеру, но из-за ленивого механизма очистки Caffeine (Lazy Maintenance) или ошибок конфигурации продолжает отдаваться клиентам.
- **Сценарий теста инвалидации (@CacheEvict):**
  1. Чтение сущности через сервис -> данные оседают в кэше (`repository.findById` вызван 1 раз).
  2. Мутация сущности через метод с `@CacheEvict` или `@CachePut`.
  3. Повторное чтение -> сервис обязан сделать повторный запрос к БД (`verify(repository, times(2))`) и вернуть обновленные данные.
- **Сценарий детерминированного тестирования TTL Expiry (Без Thread.sleep):**
  1. Внедрение виртуального времени через `Ticker` (`FakeTicker` из Guava / кастомный наносекундный генератор).
  2. Помещение записи в кэш с TTL = 15 минут.
  3. Проверка попадания в кэш на 14-й минуте (`ticker.advance(14 min)`).
  4. Сдвиг времени на 16-ю минуту (`ticker.advance(2 min)`) и вызов `cache.cleanUp()` для форсирования очистки буферов.
  5. Проверка, что `cache.getIfPresent()` возвращает `null`, а вызов бизнес-сервиса форсирует реальный поход в репозиторий.


### 5.3. Тестирование безопасности и изолированности WebSocket (STOMP Security)
- **Суть:** Проверка защиты протокола реалтайм-взаимодействия поверх WebSockets/STOMP.
- **Фокус проверок:**
  - Аутентификация на фазе CONNECT: передача валидного JWT в STOMP-заголовках, отклонение анонимных или просроченных подключений.
  - Авторизация подписок: валидация назначения (`destination`). Проверка того, что пользователь с ID `10` не может подписаться на персональный канал пользователя `20` (`/topic/chat/20` или `/user/queue/notifications`).
  - Валидация исходящих сообщений: проверка прав на отправку (`SEND`) в конкретные каналы и чат-комнаты.
