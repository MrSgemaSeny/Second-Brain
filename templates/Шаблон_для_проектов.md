## Как использовать

1. Копируй этот файл в корень каждого нового проекта.
2. Заполняй `## Текущее состояние` при каждом обновлении.
3. При работе с AI — скидывай файл целиком. AI сам определит фазу, подфазу и что делать дальше.
4. Статусы: `[ ]` не начато / `[~]` в процессе / `[x]` готово / `[-]` пропущено осознанно

### 1.3 Выбор стека

### 1.5 Репозиторий и окружение

## ФАЗА 2 — СКЕЛЕТ И AUTH

> Цель: проект деплоится, пользователь может войти. Ничего больше.

### 2.1 Backend скелет
- [ ] Проект создан (Spring Initializr / аналог)
- [ ] Подключена БД, первая миграция V1 работает
- [ ] Health endpoint `/actuator/health` или аналог отвечает
- [ ] GlobalExceptionHandler настроен — все ошибки в едином формате ApiResponse
- [ ] Логирование настроено (не System.out.println)

### 2.2 Frontend скелет
- [ ] Проект создан (Vite / аналог)
- [ ] Роутинг настроен
- [ ] API-клиент настроен (базовый fetch/axios wrapper)
- [ ] Переменные окружения: VITE_API_URL и аналоги
- [ ] Сборка проходит без ошибок

### 2.3 Auth модуль
- [ ] Регистрация / логин по email + password
- [ ] JWT в httpOnly cookie (не localStorage)
- [ ] Refresh token rotation + revocation
- [ ] Роли реализованы с первого дня
- [ ] CORS настроен корректно (не *)
- [ ] CSRF защита (X-Requested-With или аналог)
- [ ] Rate limiting на auth эндпоинтах
- [ ] Пароли через BCrypt / аналог

### 2.4 CI/CD базовый
- [ ] Push в main → автодеплой на прод
- [ ] Тесты запускаются в pipeline
- [ ] Pipeline блокируется на упавших тестах
- [ ] Секреты только в CI secrets, не в коде

### 2.5 Первый деплой
- [ ] Приложение доступно по внешнему URL
- [ ] Логин работает в проде
- [ ] Переменные окружения заданы через платформу (не в коде)
- [ ] ddl-auto=none или validate в проде (никогда create/update)

## ФАЗА 3 — CORE МОДУЛИ (MVP)

> Цель: реализовать минимальный набор функций который решает главную проблему пользователя.
> Правило: один модуль — один эпик. Используй EPIC_TEMPLATE.md.

### 3.1 Планирование MVP
- [ ] Список модулей зафиксирован (не больше 3-4 для MVP)
- [ ] Для каждого модуля создан эпик по шаблону
- [ ] Зависимости между модулями обозначены
- [ ] Out of scope зафиксирован явно

### 3.2 Для каждого модуля (повторяй)
- [ ] Миграции написаны и проверены на чистой БД
- [ ] Backend: сервис, контроллер, DTO, репозиторий
- [ ] Row-level security: пользователь видит только своё
- [ ] Smoke-тест на happy path
- [ ] Frontend: страница, API-вызовы, базовый UI
- [ ] Эпик помечен как Done

### 3.3 Качество MVP
- [ ] Нет N+1 запросов в основных эндпоинтах
- [ ] Нет raw stack trace в ответах API
- [ ] Все роли проверены: каждая видит только то что должна
- [ ] Основные сценарии протестированы вручную в проде

## ФАЗА 4 — БЕЗОПАСНОСТЬ

> Цель: продукт не стыдно показать и не страшно запустить с реальными данными.
> Это не "сделать один раз" — возвращайся сюда после каждого крупного изменения.

### 4.1 Backend security
- [ ] IDOR защита на всех batch-операциях
- [ ] Все эндпоинты закрыты нужными ролями (@PreAuthorize)
- [ ] Секреты только в env vars
- [ ] Чувствительные поля маскируются в логах (пароли, токены)
- [ ] Загрузка файлов: проверка MIME через Apache Tika или аналог
- [ ] Блокировка опасных расширений (.exe, .sh и т.д.)
- [ ] Refresh token инвалидируется при logout, смене пароля, удалении пользователя
- [ ] Rate limiting на все мутирующие эндпоинты

### 4.2 Frontend security
- [ ] Токены не хранятся в localStorage или URL
- [ ] credentials: 'include' на всех fetch-запросах
- [ ] Нет console.log с чувствительными данными в проде

### 4.3 Инфраструктура
- [ ] HTTPS везде
- [ ] Заголовки безопасности: CSP, X-Frame-Options и т.д.
- [ ] Actuator/health открыт публично, остальные закрыты
- [ ] Бэкап БД настроен и протестирован (восстановление проверено)

### 4.4 OWASP базовый чеклист
- [ ] Injection: параметризованные запросы (не конкатенация строк)
- [ ] Broken Auth: токены протухают, сессии инвалидируются
- [ ] Sensitive Data: пароли хешированы, токены в httpOnly cookie
- [ ] Broken Access Control: row-level security, IDOR защита
- [ ] Security Misconfiguration: нет дефолтных паролей, нет открытых debug-эндпоинтов

## ФАЗА 5 — КАЧЕСТВО И ТЕСТЫ

> Цель: уверенность что рефакторинг и новые фичи не ломают старое.

### 5.1 Backend тесты
- [ ] Smoke-тесты на все основные flow (register → login → действие)
- [ ] Unit-тесты на сервисы с нетривиальной логикой
- [ ] Integration-тесты на security boundaries (кто что видит)
- [ ] Тест на IDOR: пользователь A не может получить данные пользователя B
- [ ] Все тесты проходят на чистой БД (без зависимости от порядка)

### 5.2 Frontend тесты
- [ ] Unit-тесты на компоненты с логикой
- [ ] Тесты на критичные пользовательские сценарии

### 5.3 Качество кода
- [ ] Нет дублирования бизнес-логики между сервисами
- [ ] Нет прямых SQL-запросов там где должен быть репозиторий
- [ ] Нет TODO/FIXME в проде без issue
- [ ] Импорты чистые, нет неиспользуемых зависимостей
