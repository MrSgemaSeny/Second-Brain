## 3. Архитектура обработки сообщений (Message Pipeline)

Чат для трансляций — это не просто "получил строку — разослал всем". Это сложный пайплайн обработки.

### 3.1 Publisher-Subscriber (Pub/Sub) Паттерн
Каждый зритель, открывший страницу трансляции, устанавливает WebSocket соединение и подписывается на "глобальный топик" (Global Room).
Когда зритель отправляет сообщение, оно проходит следующий путь:

1. **Ingress (Входной узел):** Сообщение принимается WebSocket-хэндлером.
2. **Rate Limiting:** Защита от флуда. Если пользователь отправляет более 3 сообщений в секунду, он получает shadow-ban или временный мут (Token Bucket алгоритм).
3. **Profanity Filter & Moderation:** 
   - Проверка по словарю нецензурной лексики.
   - Возможно, вызов внешнего API машинного обучения для определения токсичности.
4. **Broadcasting (Рассылка):** Сообщение помещается в очередь (Message Broker), откуда worker-потоки рассылают его всем активным WebSocket-сессиям.

### 3.2 Директория `logs`
Наличие выделенной директории `logs` в корне проекта говорит о серьезном отношении к Observability (наблюдаемости).
В таких системах используется асинхронное логирование (AsyncAppender в Logback или Log4j2 LMAX Disruptor), чтобы запись логов на диск (I/O операция) не блокировала основной Event Loop.
Логируются:
- Факты подключения/отключения.
- Ошибки сокетов (Broken pipe, Connection reset by peer).
- Сами сообщения (для юридической модерации и аналитики).

### 3.3 Директория `query`
Эта папка хранит SQL/NoSQL скрипты. В высоконагруженных чатах сохранение каждого сообщения в традиционную реляционную БД (PostgreSQL) синхронно — это "убийство" базы данных.
*Вероятная реализация:* Сообщения кэшируются в памяти или Redis (In-Memory Data Grid), а затем сбрасываются (Flush) в БД батчами (Batch Insert) по таймеру каждые 5 секунд с использованием предварительно скомпилированных `PreparedStatement` (которые, возможно, хранятся в папке `query`).
