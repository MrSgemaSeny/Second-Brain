## 12. Правила разработки

### 12.1 Принципы

**Security first** — безопасность важнее функциональности и производительности. Любое решение взвешивается с учётом security implications.

**Working over perfect** — работающий MVP важнее идеальной архитектуры. Рефакторинг делается, когда появляется понимание, что именно нужно улучшать.

**No premature optimization** — оптимизация делается при наличии измеримой проблемы, а не на основе предположений.

**Token efficiency** (для AI-агентов) — минимальное количество tool calls для решения задачи. Не читать файлы целиком, если нужна одна функция.

### 12.2 Git Workflow

Используется trunk-based development с основной веткой main:
1. Все изменения ведутся в main (для текущего этапа развития)
2. При фиксе багов или завершении задач — коммит и push в main
3. CI/CD автоматически деплоит после прохождения тестов

Сообщения коммитов:
```
feat(US-02.1): добавить создание подзадач в задачах
fix(US-09.2): исправить валидацию TOTP-кода
migration(V111): добавить индекс для часто-запрашиваемых задач
docs: обновить RUNBOOK
```

### 12.3 Code Style

Java код следует стандартным convetions с акцентом на читаемость. Фронтенд использует ESLint и Prettier для автоматического форматирования. TypeScript strict mode включён.

Основные правила:
- Имена классов — PascalCase (TaskService)
- Имена методов — camelCase (createTask)
- Имена констант — UPPER_SNAKE_CASE (MAX_RETRY_COUNT)
- Имена файлов — kebab-case (task-service.ts)
- Геттеры/setters не используются без необходимости
- Preference к immutability

### 12.4 Code Review

При работе с AI-агентами code review выполняется агентом автоматически. Для человеческого review:
- Проверка security implications
- Проверка соответствия архитектуре
- Проверка обработки edge cases
- Проверка тестового покрытия

### 12.5 Запрещённые практики

- Изменение применённых Flyway миграций
- Использование @PostConstruct для DB-операций
- Хардкод секретов в исходном коде
- Использование @Entity для объектов, не являющихся таблицами
- Создание God-classes с тысячами строк
- Игнорирование Exception handling
- SQL-инъекции через конкатенацию строк
- XSS через вывод непроверенного HTML

### 12.6 Error Handling

Все исключения перехватываются централизованным ExceptionHandler. Типы ошибок:
- ApiException — бизнес-ошибки с кодом и сообщением
- NotFoundException — ресурс не найден (404)
- AccessDeniedException — недостаточно прав (403)
- ValidationException — ошибка валидации (400)
- Все прочие — UnexpectedException (500)

Raw stack trace никогда не возвращается клиенту в production.
