## 6. База данных и миграции

### 6.1 Структура миграций

Flyway миграции располагаются в `zhan-finance-backend/src/main/resources/db/migration/` и именуются по шаблону `V{NN}__{description}.sql`, где NN — порядковый номер миграции, description — краткое описание на английском языке. Двойное подчёркивание между номером и описанием — требование Flyway.

Текущая цепочка миграций простирается от V1 до V110+. Каждая миграция добавляет новую функциональность: таблицы, колонки, индексы, данные. Старые миграции никогда не модифицируются после применения — это критическое правило.

### 6.2 Неизменяемость миграций

Flyway хранит checksum каждой применённой миграции в таблице flyway_schema_history. Изменение файла миграции приводит к несовпадению checksum и ошибке при запуске приложения. Это защитный механизм — он предотвращает случайное изменение схемы production-базы.

Если требуется изменить существующую структуру, создаётся новая миграция. Например, если нужно добавить колонку email_phone в таблицу clients, создаётся файл V111__add_phone_to_clients.sql с соответствующим ALTER TABLE.

### 6.3 Правила именования

Рекомендуемые префиксы для миграций:
- V{NN}__create_{table}.sql — создание таблицы
- V{NN}__add_{column}_to_{table}.sql — добавление колонки
- V{NN}__create_{index}_index.sql — создание индекса
- V{NN}__insert_{data}.sql — вставка начальных данных (сидинг)

### 6.4 Сидинг данных

Первичные данные (сидеры) создаются не через миграции, а через Spring-компоненты с аннотацией @EventListener(ApplicationReadyEvent.class). Это обеспечивает корректный порядок выполнения: миграции сначала, затем сидинг.

Пример: PipelineSeederService создаёт стандартные воронки после запуска приложения. @PostConstruct для сидинга использовать запрещено — это вызывает race condition с Flyway.

### 6.5 Локальная разработка

При локальной разработке используется baseline для существующей схемы. В application-dev.yml настроено `spring.flyway.baseline-version=110`, что позволяет применять новые миграции (V111+) к существующей БД без ошибок baseline.

### 6.6 Основные таблицы

Таблица app_users хранит пользователей системы. Таблица refresh_tokens связывает пользователей с refresh-токенами. Таблица tasks, stages, pipelines управляют CRM-функциональностью. Таблицы invoices, subscriptions обрабатывают биллинг. Таблицы courses, chapters, lessons, enrollments реализуют LMS. Таблицы documents, document_templates, stored_files обеспечивают документооборот. Таблица chat_messages хранит сообщения. Таблица notifications управляет уведомлениями. Таблица audit_log журналирует действия.

### 6.7 Индексы и оптимизация

Критические запросы оптимизированы через индексы:
- idx_tasks_assigned_user_id — поиск задач по исполнителю
- idx_tasks_client_id — задачи клиента
- idx_tasks_stage_id — задачи по стадии
- idx_refresh_tokens_user_id — поиск токенов пользователя
- idx_two_factor_pre_auth_expires_at — очистка просроченных записей

### 6.8 Триггеры защиты аудита

PostgreSQL триггеры на таблицах audit_log запрещают UPDATE и DELETE:
```sql
CREATE OR REPLACE FUNCTION prevent_audit_modification()
RETURNS TRIGGER AS $$
BEGIN
  RAISE EXCEPTION 'UPDATE and DELETE on audit tables are prohibited';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER audit_log_no_update
  BEFORE UPDATE ON audit_log
  FOR EACH ROW EXECUTE FUNCTION prevent_audit_modification();
```
