## 7. Безопасность и авторизация

### 7.1 Многоуровневая защита

Безопасность платформы реализована на нескольких уровнях. Network layer защищён через HTTPS на всех окружениях и Firewall на уровне инфраструктуры. Transport layer использует TLS для шифрования трафика. Application layer включает аутентификацию, авторизацию, rate limiting и валидацию ввода. Data layer обеспечивает row-level security и защиту аудита.

### 7.2 JWT-аутентификация

Access-токен содержитclaims: sub (user_id), email, roles[], iat (issued at), exp (expiration). Токен подписывается секретным ключом через HMAC-SHA256 и передаётся в заголовке Authorization: Bearer <token>. JwtService валидирует подпись и срок жизни токена при каждом запросе.

Refresh-токен хранится в httpOnly cookie и отправляется автоматически браузером. Это защищает от XSS-атаки (токен недоступен JavaScript). SameSite=strict предотвращает отправку cookie в cross-site запросах.

### 7.3 Row-Level Security (CrmAccessService)

Spring Security @PreAuthorize проверяет только роли: hasRole('ADMIN'), hasRole('EMPLOYEE'). Но этого недостаточно — сотрудник EMPLOYEE не должен видеть задачи других сотрудников. CrmAccessService реализует дополнительную проверку на уровне записей.

Пример проверки в TaskService:
```java
public TaskDto updateTask(Long taskId, TaskUpdateRequest request, Long userId) {
  Task task = taskRepository.findById(taskId)
    .orElseThrow(() -> new NotFoundException("Task not found"));
  
  // Row-level check
  if (!crmAccessService.canAccessTask(userId, task)) {
    throw new AccessDeniedException("You don't have access to this task");
  }
  
  // Business logic
  // ...
}
```

### 7.4 IDOR-защита на batch-операциях

Массовые операции (назначение нескольких задач, изменение статуса нескольких задач) требуют проверки доступа к каждому элементу отдельно. TaskBatchOperationRequest содержит список ID, и сервис итерирует по ним, проверяя доступ к каждому.

### 7.5 Rate Limiting

Bucket4j реализует token bucket algorithm для ограничения частоты запросов. ApiRateLimitFilter применяется ко всем эндпоинтам: 100 запросов в минуту с одного IP. AuthRateLimitFilter строже для auth-эндпоинтов: 5 попыток логина в минуту, 3 попытки регистрации в минуту.

При превышении лимита возвращается HTTP 429 Too Many Requests с заголовком Retry-After.

### 7.6 Input Validation

Все входные данные валидируются через Jakarta Validation annotations (@NotBlank, @Email, @Size, @Pattern). Сервисы не доверяют входным данным и повторно валидируют их при необходимости.

### 7.7 Output Encoding

JSON-ответы не содержат raw HTML — фронтенд отвечает за экранирование при отображении. PDF и DOCX документы генерируются через шаблонизаторы, которые автоматически экранируют пользовательский ввод.

### 7.8 Защита чувствительных данных

HibernateAuditListener маскирует SENSITIVE_FIELDS при записи в audit_log. К таким полям относятся: password, totpSecret, refreshToken. Bcrypt используется для хеширования паролей с cost factor 12.

### 7.9 2FA (TOTP)

Двухфакторная аутентификация реализована на основе RFC 6238 (TOTP). При настройке 2FA генерируется секрет (base32), создаётся QR-код с otpauth:// URI для сканирования приложением-аутентификатором. При логине после ввода пароля запрашивается 6-значный код, который валидируется через Time-based One-Time Password Algorithm.

Резервные коды (8 кодов по 10 символов) позволяют войти при утере устройства. Коды одноразовые — после использования удаляются.
