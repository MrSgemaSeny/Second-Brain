## 3. Архитектура системы

### 3.1 Общая архитектура

Система построена по классической трехслойной архитектуре с разделением на presentation layer (фронтенд), application layer (бэкенд API) и data layer (PostgreSQL). Фронтенд представляет собой stateless SPA, которое взаимодействует с бэкендом исключительно через REST API и WebSocket. Бэкенд не хранит состояние сессий на сервере — вся информация о пользователе инкапсулирована в JWT-токене.

Клиент отправляет запросы на API, где они проходят через цепочку фильтров Spring Security (аутентификация, авторизация, rate limiting), затем попадают в контроллер соответствующего модуля, обрабатываются сервисом с возможным обращением к базе данных через репозитории, и ответ возвращается клиенту в формате JSON.

### 3.2 Архитектура бэкенда

Бэкенд организован модульно внутри пакета `com.example.zhanfinancebackend.modules`. Каждый модуль содержит типичную для Spring MVC структуру: controller (REST-эндпоинты), service (бизнес-логика), repository (доступ к данным), entity (JPA-сущности), dto (объекты передачи данных) и mapper (преобразователи между entity и dto).

Все API запросы проходят через контекстный путь `/api` и версионированы как `/v1/**`, что даёт итоговые пути `/api/v1/...`. Версионирование позволяет развивать API без ломания существующих интеграций — клиенты могут продолжать использовать старую версию, пока мигрируют на новую.

Общие компоненты вынесены в пакеты `common/` и `config/`:
- common/audit — Hibernate-слушатели для автоматического журналирования изменений
- common/config — базовые конфигурации приложения
- common/exception — централизованная обработка исключений
- common/filter — HTTP-фильтры (CORS, авторизация)
- common/response — стандартизированные ответы API

### 3.3 Архитектура фронтенда

Фронтенд следует методологии Feature-Sliced Design, которая решает проблему организации кода в больших приложениях. Структура слоёв:

- **app/** — инициализация приложения, провайдеры контекста (AuthContext, QueryClientProvider), роутер
- **pages/** — страницы приложения, соответствующие маршрутам (LoginPage, DashboardPage, AdminEmployeesPage, TasksPage)
- **widgets/** — крупные самостоятельные блоки UI (TaskKanbanBoard, DocumentViewer, ChatWidget)
- **features/** — пользовательские сценарии, инкапсулирующие логику фичи (contact-form, auth, 2fa-setup)
- **entities/** — бизнес-сущности с их моделями, API-клиентами и хуками (task, client, user, course)
- **shared/** — переиспользуемый код: api/http (обёртка запросов), ui (базовые компоненты), lib (утилиты), i18n (локализация)

### 3.4 Паттерны проектирования

В проекте применяются проверенные паттерны проектирования. Паттерн Repository используется для абстракции доступа к данным — каждый репозиторий наследует JpaRepository и может содержать кастомные запросы через @Query. Паттерн Service Layer инкапсулирует бизнес-логику, отделяя её от контроллеров и обеспечивая транзакционность. Паттерн DTO (Data Transfer Object) используется для передачи данных между слоями, что позволяет контролировать видимость полей и версионировать API. Паттерн Mapper преобразует объекты между слоями (Entity -> DTO, DTO -> Entity), используя MapStruct или ручные мапперы.

### 3.5 Поток данных аутентификации

Процесс аутентификации начинается с отправки учётных данных на эндпоинт `/api/v1/auth/login`. AuthService проверяет credentials, при необходимости запрашивает верификацию 2FA, и возвращает access-токен (в теле ответа) и refresh-токен (в httpOnly cookie). Access-токен содержит информацию о пользователе (id, email, роли) и имеет короткий срок жизни (1 час). Refresh-токен используется для получения нового access-токена без повторного ввода пароля и имеет срок жизни 7 дней.

При каждом запросе JwtAuthenticationFilter перехватывает Bearer-токен из заголовка Authorization, валидирует его через JwtService, извлекает информацию о пользователе и устанавливает SecurityContext для авторизации.

### 3.6 Кэширование

Caffeine cache используется для кэширования данных на уровне приложения с per-region политикой. Регион — это логическая группа кэшируемых данных, например, "pipelines" для пайплайнов CRM или "documents" для шаблонов документов. CacheConfig определяет настройки каждого региона: максимальный размер, время жизни записей, политику вытеснения.

Преимущества Caffeine перед Ehcache или Redis: интеграция с Spring, низкий overhead, синхронный доступ без сериализации, простота конфигурации. Недостаток — отсутствие распределённого кэша, что приемлемо для текущего масштаба приложения (single-instance deployment).
