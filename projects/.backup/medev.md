## 1. Введение и обзор проекта

### 1.1 Что это такое
MeDev — это data-first платформа для разработчиков. 
Основная проблема текущих инструментов: разработчики тратят часы на поддержание своего резюме (в Word, Canva или кривых генераторах), отдельного сайта-портфолио и профиля на GitHub. Все эти ресурсы не синхронизированы, и данные приходится дублировать.
MeDev решает эту проблему созданием единого, централизованного профиля (Single Source of Truth). Разработчик один раз загружает свои данные (или платформа парсит их из GitHub/старого PDF-резюме), после чего может автоматически генерировать красивые PDF-резюме, делиться ссылкой на стильное веб-портфолио и выгружать README для GitHub.

### 1.2 Основные возможности (Киллер-фичи)
- **Data-First подход**: Данные хранятся абстрактно от представления. Один профиль → множество форматов вывода.
- **Интеграция с GitHub**: Автоматическое подтягивание репозиториев, статистики активности (коммиты, pull requests) и используемых языков программирования через GitHub API.
- **Интеллектуальный парсинг резюме**: Загрузка старого PDF-резюме и извлечение из него текста с последующим маппингом в структурированный профиль (с помощью Apache Tika/PDFBox).
- **Продвинутый конструктор резюме**: Визуальный drag-and-drop редактор секций (построенный на `dnd-kit`). Пользователь решает, какие блоки показывать, а какие скрывать, не удаляя данные.
- **Публичное веб-портфолио**: Готовая стильная страница вида `medev.app/username`, которая адаптирована под мобильные устройства и служит заменой личному сайту-визитке.
- **Экспорт PDF**: Генерация резюме на основе HTML/CSS-шаблонов с рендерингом на сервере (Thymeleaf + Flying Saucer).

### 1.3 Целевая аудитория и монетизация
- **Аудитория**: Разработчики уровней Junior, Middle, Senior. Студенты, ищущие первую работу. На старте — рынок СНГ, затем — глобальный рынок.
- **Монетизация (Freemium)**: 
  - **Free**: 3 генерации резюме в день, 1 шаблон, лого MeDev на странице, ватермарк на PDF.
  - **Pro**: Безлимитные генерации, все шаблоны, кастомные секции, экспорт GitHub README, отсутствие ватермарков. Платная подписка (Stripe для мира, Kaspi Pay для СНГ).

## 2. Технологический стек

### 2.1 Бэкенд (Java/Spring Boot)
- **Язык и фреймворк**: Java 17, Spring Boot 3.3.0. Выбор обоснован надежностью и готовностью к production.
- **База данных**: PostgreSQL. Надежная реляционная БД для хранения структурированных профилей.
- **Миграции**: Flyway. Строгий контроль схемы БД (8 базовых таблиц создаются через `V1`-`V8` скрипты).
- **Кэширование**: Redis. Используется для хранения refresh-токенов, кэширования ответов от GitHub API (чтобы не упираться в лимиты) и хранения временных стейтов.
- **Безопасность**: Spring Security, JWT (access/refresh токены).
- **PDF-генерация**: Thymeleaf (шаблонизация) + Flying Saucer (HTML to PDF) + PDFBox (для парсинга входящих файлов).

### 2.2 Фронтенд (React/Vite)
- **База**: React 19, TypeScript, Vite. Обеспечивают максимальную скорость разработки и строгую типизацию.
- **Архитектура**: Feature-Sliced Design (FSD). Разделение на layers (app, pages, features, entities, shared).
- **Стейт-менеджмент**: React Query (для серверного стейта и кэширования API-запросов) + Zustand (для локального стейта сложного drag-and-drop редактора).
- **Стилизация**: Tailwind CSS v4. Быстрая компонентная стилизация.
- **Интерактив**: `@dnd-kit/core` для реализации drag-and-drop сортировки секций в редакторе резюме.

### 2.3 Инфраструктура и деплой
- **Backend Deployment**: Fly.io (контейнеризация, авто-SSL).
- **Frontend Deployment**: GitHub Pages.
- **CI/CD**: GitHub Actions. Автоматический прогон тестов (`./gradlew test`) и автодеплой на Fly.io при слиянии в ветку `main`.
- **Платежи**: Stripe API + вебхуки.

## 3. Архитектура системы

### 3.1 Общая архитектура (Модульный монолит)
Система спроектирована как **модульный монолит** (Modular Monolith) на бэкенде. Это позволяет избежать излишней сложности микросервисов на старте, но сохраняет границы контекстов (Auth, Profile, GitHub, Resume, Billing), что позволит легко разделить монолит в будущем.
Бэкенд полностью **stateless** — авторизация работает через JWT токен. Сессионная информация (refresh-токены) лежит в Redis.

### 3.2 Структура БД
Схема БД строго реляционная. Все таблицы связаны с профилем по `profile_id`.
Ключевые таблицы:
1. `users`: Базовая информация (email, password, username, role, plan).
2. `profiles`: Детали профиля (имя, summary, контакты, github_token, is_public).
3. `experience`: Опыт работы. Связь 1-ко-Многим с profiles.
4. `education`: Образование.
5. `skills`: Навыки (языки программирования, технологии).
6. `languages`: Владение человеческими языками (Английский, Казахский и т.д.).
7. `projects`: Проекты (с ссылками на репо, демо, описанием).
8. `subscriptions`: Данные о подписке Pro (Stripe Customer ID).

Все миграции идут через Flyway. Строгий запрет на использование `ddl-auto=update` в production.

## 4. Модули системы (Детальный разбор)

### 4.1 Auth Module (Авторизация)
- **Функционал**: Регистрация, логин, обновление сессии, logout.
- **Особенности**: Выдача Access Token (JWT, 24 часа) и Refresh Token (Redis, 30 дней). Логин возможен как через Email/Pass, так и через GitHub OAuth. При регистрации автоматически создается пустая запись в `profiles`.

### 4.2 Profile Module (Профиль и сущности)
- **Функционал**: CRUD-операции над профилем и его секциями (опыт, навыки, проекты).
- **Особенности**: Безопасность на уровне строк (Row-Level Security) реализована через проверки в сервисах: каждый запрос обновляет данные только для `SecurityUtils.getCurrentUserId()`. Наличие эндпоинта `reorder` для сохранения порядка секций, настроенного в drag-and-drop редакторе.

### 4.3 GitHub Module (Интеграция)
- **Функционал**: Запрос данных у GitHub API по OAuth токену пользователя.
- **Особенности**: Парсинг языков из всех репозиториев и формирование статистики. Кэширование ответов от GitHub в Redis на 1 час (чтобы не исчерпать Rate Limit в 5000 запросов/час).

### 4.4 Resume Module (Генерация и парсинг)
- **Функционал**: Превращение профиля в PDF и загрузка старого PDF в систему.
- **Особенности**: Для генерации PDF используется Thymeleaf. Профиль "впрыскивается" в HTML-шаблон (например, `classic.html`), затем Flying Saucer рендерит его в байтовый массив PDF. Ограничение для Free-пользователей проверяется через счетчики в Redis (`resume:gen:userId:date`).

### 4.5 Portfolio Module (Публичная визитка)
- **Функционал**: Выдача данных для страницы `medev.app/{username}`.
- **Особенности**: Это единственный полностью открытый эндпоинт (без JWT). Возвращает агрегированный DTO. Если профиль отмечен как `is_public = false`, API возвращает 404, не раскрывая существование пользователя.

### 4.6 Billing Module (Монетизация)
- **Функционал**: Обработка подписок и интеграция со Stripe.
- **Особенности**: Генерация ссылок на оплату (`CheckoutSession`), обработка вебхуков от Stripe (`checkout.session.completed`, `customer.subscription.deleted`) для выдачи или отзыва Pro-статуса.

## 5. Ролевая модель и безопасность

### 5.1 Роли
- **USER**: Обычный разработчик. Может редактировать только свой профиль.
- **ADMIN**: Администратор системы. Имеет доступ к статистике, управлению пользователями и шаблонами резюме.

### 5.2 Защита данных
- **IDOR Protection**: Все эндпоинты профиля (`/v1/profile/**`) не принимают `userId` из параметров URL. Вместо этого он извлекается строго из проверенного JWT-токена в бэкенде.
- **Скрытые исключения**: Наличие `GlobalExceptionHandler`. Система не отдает сырые StackTrace на клиент. Все ошибки маппятся в стандартизированный JSON (`code`, `message`).
- **Секреты**: Токены GitHub хранятся в зашифрованном виде в БД. Все ключи API (Stripe, JWT Secret) лежат строго в переменных окружения.

## 7. Риски и Подводные камни

1. **PDF с кириллицей (Flying Saucer)**: Встроенные шрифты могут не поддерживать русский язык. Обязательно встраивать `.ttf` (например, Roboto) через `@font-face` прямо в HTML-шаблоны.
2. **GitHub API Rate Limits**: Критически важно соблюдать кэширование, иначе пользователи быстро "положат" квоту на генерацию статистики.
3. **Парсинг старых PDF**: Данные из резюме часто неструктурированны. Ожидается точность парсинга в районе 60-70%. Главное правило — пользователь должен подтверждать и редактировать распознанные данные.
4. **Drag-and-Drop на мобильных**: dnd-kit требует явного подключения `TouchSensor` для тачскринов. Редактор резюме сложен на смартфонах, поэтому primary device для редактирования — десктоп.

## 8. UX Принципы

1. **Zero friction onboarding**: Регистрация через GitHub должна моментально создавать базовый профиль, готовый к просмотру.
2. **Real-time preview**: Любое изменение в редакторе (добавление навыка, скрытие опыта) должно мгновенно отображаться в превью резюме (внутри iframe).
3. **Сохранность данных**: Скрытие секции в резюме — это только изменение флага видимости, удалять данные из БД нельзя.
